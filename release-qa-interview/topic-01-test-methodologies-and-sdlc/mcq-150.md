## Part 1 — SDLC Fundamentals and Models (30 questions)

### SDLC basics

#### MCQ 1. Which phase of the SDLC establishes what the product must do and the constraints it must meet?

A. Design
B. Requirements analysis
C. Implementation
D. Maintenance

<details>
<summary>Show answer</summary>

**Correct answer: B.** Requirements analysis defines the needed behavior and constraints. Design decides how to satisfy them, implementation builds the solution, and maintenance changes it after release.

</details>

#### MCQ 2. A team finds during system testing that a requirement conflicts with a regulatory rule. Which phase should have caught this first?

A. Requirements analysis
B. Implementation
C. System testing
D. Maintenance

<details>
<summary>Show answer</summary>

**Correct answer: A.** Requirement reviews should compare the requirement with regulatory constraints before design begins. Finding the conflict in system testing means the flaw was inherited by every later phase and must now be fixed late.

</details>

#### MCQ 3. What is the main difference between the SDLC and the STLC?

A. The SDLC is for developers, and the STLC is for testers.
B. The SDLC covers the product lifecycle; the STLC is the testing workstream inside it.
C. The STLC replaces the SDLC in Agile projects.
D. The SDLC ends at deployment; the STLC ends at test closure.

<details>
<summary>Show answer</summary>

**Correct answer: B.** The SDLC spans the product from concept to retirement, while the STLC is the testing lifecycle that runs alongside it. Option D is the nearest trap: both continue after deployment through maintenance and production feedback.

</details>

#### MCQ 4. Which STLC activity can begin during requirements analysis?

A. Test execution
B. Production monitoring
C. Test design and planning
D. Incident review

<details>
<summary>Show answer</summary>

**Correct answer: C.** Test design and planning can start as soon as requirements are reviewable, because acceptance criteria are what tests will be built from. Execution needs a build, and production monitoring and incident review happen after release.

</details>

#### MCQ 5. Why is "the testing phase" an incomplete description of QA work in an SDLC?

A. Testing only happens after deployment.
B. Testing is entirely automated.
C. QA only writes test cases.
D. QA also reviews requirements, designs tests, and prepares environments before execution.

<details>
<summary>Show answer</summary>

**Correct answer: D.** Test execution is only one part of QA work; reviews, test design, environment preparation, and regression planning happen across the lifecycle. Options A, B, and C are false absolutes that ignore those earlier and later activities.

</details>

#### MCQ 6. A release has a compressed test window because requirements were finalized late. Which lifecycle risk does this illustrate?

A. Too much test automation
B. Excessive regression coverage
C. Late feedback compressing verification time
D. Overstaffed QA

<details>
<summary>Show answer</summary>

**Correct answer: C.** Late requirements push design, development, and testing to the right, shrinking the time available for verification. The durable fix is earlier QA involvement and review, not simply compressing testing harder.

</details>

### Waterfall

#### MCQ 7. Which statement best describes the Waterfall model?

A. Overlapping iterations with continuous feedback
B. Sequential phases with approval gates and formal change control
C. Risk-driven loops with prototypes
D. Continuous deployment with feature flags

<details>
<summary>Show answer</summary>

**Correct answer: B.** Waterfall completes and approves each phase before the next one begins, with formal change control. Overlapping iterations describe iterative or Agile work, risk-driven loops describe the spiral model, and feature flags belong to continuous delivery.

</details>

#### MCQ 8. What is a typical QA disadvantage of Waterfall?

A. Too much early feedback
B. Requirements are never documented
C. Testing starts before design
D. Defects surface late and changes are expensive

<details>
<summary>Show answer</summary>

**Correct answer: D.** Waterfall usually places test execution after implementation, so requirement and design defects surface late and require expensive rework. Options A, B, and C invert the model: Waterfall documents heavily and tests late, not early.

</details>

#### MCQ 9. When is Waterfall most appropriate?

A. Requirements are stable and change is expensive
B. Requirements change every day
C. The team wants continuous delivery
D. The product is a throwaway prototype

<details>
<summary>Show answer</summary>

**Correct answer: A.** Waterfall fits stable, well-understood scope where change is costly and documentation matters. Rapidly changing requirements, continuous delivery, and throwaway prototypes all favor iterative or incremental approaches.

</details>

#### MCQ 10. A regulated hardware release has fixed contractual requirements and mandatory documentation. Which lifecycle fits best?

A. Waterfall
B. Pure Scrum with daily production releases
C. Exploratory testing with no plan
D. Continuous deployment with feature flags

<details>
<summary>Show answer</summary>

**Correct answer: A.** Fixed scope, expensive change, and documentation requirements align with Waterfall. The other options assume rapid change, frequent releases, or operational practices that the described constraints do not support.

</details>

### V-model

#### MCQ 11. In the V-model, which test level corresponds to the requirements phase?

A. Unit testing
B. Integration testing
C. System testing
D. Acceptance testing

<details>
<summary>Show answer</summary>

**Correct answer: D.** Requirements are verified by acceptance testing, system design by system testing, architecture by integration testing, and module design by unit testing. The V pairs each left-side development level with its right-side verification level.

</details>

#### MCQ 12. In the V-model, what is the main purpose of entry criteria?

A. To decide when a test level may start
B. To decide when a test level may finish
C. To assign defect priority
D. To select automation tools

<details>
<summary>Show answer</summary>

**Correct answer: A.** Entry criteria confirm the preconditions for starting a level, such as approved artifacts, a ready environment, and test data. Option B describes exit criteria, which decide when the level may finish.

</details>

#### MCQ 13. Which is a limitation of the V-model?

A. It cannot document requirements
B. It is sequential and handles late change poorly
C. It has no test levels
D. It forbids reviews

<details>
<summary>Show answer</summary>

**Correct answer: B.** The V-model's sequential structure means late requirement changes cascade through designs and tests. The other options are false: the model is documentation-heavy and explicitly defines test levels and reviews.

</details>

#### MCQ 14. A V-model team writes acceptance tests during requirements analysis. What is the main benefit?

A. It removes the need for system testing
B. It guarantees zero defects
C. It confirms the requirement is testable and plans the right level early
D. It replaces user acceptance testing

<details>
<summary>Show answer</summary>

**Correct answer: C.** Early acceptance-test design exposes ambiguous requirements and confirms that each requirement can be verified at the right level. It does not remove system testing, guarantee zero defects, or replace the act of user acceptance testing.

</details>

### Iterative, incremental, and spiral

#### MCQ 15. What is the difference between iterative and incremental development?

A. Iterative delivers functional slices; incremental repeats refinement cycles.
B. Iterative repeats refinement cycles; incremental adds functional slices.
C. They are identical.
D. Incremental is only for hardware.

<details>
<summary>Show answer</summary>

**Correct answer: B.** Iteration refines the product repeatedly, while increment adds functional slices; the two are often combined. Option A reverses the definitions, and option D is a false constraint.

</details>

#### MCQ 16. Which model is risk-driven and builds prototypes in repeated loops?

A. Waterfall
B. V-model
C. Spiral
D. Big-bang integration

<details>
<summary>Show answer</summary>

**Correct answer: C.** The spiral model runs repeated loops with explicit risk analysis, prototypes, and evaluation. Big-bang integration is an integration strategy, not a lifecycle model.

</details>

#### MCQ 17. In an incremental lifecycle, what must QA plan explicitly because no single increment owns it?

A. Unit test naming
B. Office seating
C. Source control branching
D. Cross-increment integration and end-to-end flows

<details>
<summary>Show answer</summary>

**Correct answer: D.** Each increment can pass its own tests while integration and end-to-end behavior break across increments. Those cumulative checks need an explicit owner and plan; the other options are unrelated to lifecycle risk.

</details>

#### MCQ 18. A product must deliver value early while requirements remain uncertain. Which approach fits best?

A. Waterfall with a long test phase
B. Iterative/incremental delivery with a growing regression suite
C. A single big-bang release at the end
D. Skipping regression to save time

<details>
<summary>Show answer</summary>

**Correct answer: B.** Uncertain requirements and a need for early value favor iterative, incremental delivery, with regression growing as the product grows. Waterfall and a single big-bang release delay feedback, and skipping regression accumulates risk.

</details>

### Agile and Scrum

#### MCQ 19. Which statement best describes Agile?

A. A fixed process with no planning
B. A set of values and principles emphasizing short feedback loops and working software
C. A test design technique
D. A replacement for the SDLC

<details>
<summary>Show answer</summary>

**Correct answer: B.** Agile is a set of values and principles; Scrum is one framework that implements them. Option A is a caricature, and options C and D confuse a mindset with a technique or lifecycle.

</details>

#### MCQ 20. In Scrum, who prioritizes the product backlog?

A. Scrum Master
B. QA lead
C. Product Owner
D. Developers

<details>
<summary>Show answer</summary>

**Correct answer: C.** The Product Owner owns the product backlog and its ordering. The Scrum Master facilitates the process, and the developers build the increment; neither owns backlog priority.

</details>

#### MCQ 21. What is the Scrum Master's main responsibility?

A. Writing all tests
B. Facilitating the process and removing impediments
C. Approving releases
D. Prioritizing the backlog

<details>
<summary>Show answer</summary>

**Correct answer: B.** The Scrum Master is a facilitator who helps the team follow Scrum and removes blockers. Prioritizing the backlog belongs to the Product Owner, and release approval is a business decision.

</details>

#### MCQ 22. Which Scrum ceremony is the best place for QA to size testing work and clarify acceptance criteria?

A. Daily Scrum
B. Sprint retrospective
C. Deployment
D. Sprint planning

<details>
<summary>Show answer</summary>

**Correct answer: D.** Sprint planning selects the work and is where acceptance criteria and testing effort are clarified. The Daily Scrum coordinates progress, the retrospective improves process, and deployment is not a Scrum ceremony.

</details>

#### MCQ 23. What is the definition of done used for?

A. Defining the shared quality checklist for a completed item
B. Listing all possible defects
C. Replacing acceptance criteria
D. Setting the release date

<details>
<summary>Show answer</summary>

**Correct answer: A.** The definition of done is the team's shared standard for completion, including testing and review expectations. Acceptance criteria describe specific behavior, and the definition of done neither lists defects nor sets release dates.

</details>

#### MCQ 24. A team marks a story done because the code is merged, but no tests ran and acceptance criteria are unverified. Which artifact should prevent this?

A. Product vision
B. Burndown chart
C. Definition of done
D. Risk register

<details>
<summary>Show answer</summary>

**Correct answer: C.** The definition of done should require tests and verified acceptance criteria before an item is called complete. A burndown chart tracks remaining work, not quality, and a vision or risk register does not gate completion.

</details>

#### MCQ 25. Which Scrum artifact contains the prioritized stories and acceptance criteria?

A. Sprint backlog
B. Increment
C. Definition of done
D. Product backlog

<details>
<summary>Show answer</summary>

**Correct answer: D.** The product backlog is the ordered list of stories and their acceptance criteria. The sprint backlog is the selected subset and tasks, the increment is the result, and the definition of done is the completion standard.

</details>

#### MCQ 26. In Scrum, why does delivering an increment every sprint not automatically mean a release?

A. Increments must still meet release criteria, dependencies, and cumulative risk.
B. Releases can only happen once a year.
C. QA cannot test in Scrum.
D. The Product Owner cannot decide scope.

<details>
<summary>Show answer</summary>

**Correct answer: A.** A release is a business and quality decision that considers cumulative regression, dependencies, non-functional readiness, and accepted risk. The other options are false rules that Scrum does not impose.

</details>

### Shift-left, shift-right, DevOps, and release vs deployment

#### MCQ 27. Which practice is an example of shift-left testing?

A. Canary releases in production
B. Post-incident reviews
C. Reviewing requirements and writing tests before code
D. Synthetic monitoring

<details>
<summary>Show answer</summary>

**Correct answer: C.** Shift-left moves quality activities earlier, such as requirement review and test design before implementation. Canary releases, incident reviews, and synthetic monitoring are shift-right or production feedback practices.

</details>

#### MCQ 28. Which practice is an example of shift-right testing?

A. Unit tests in continuous integration
B. Requirements review
C. Test data preparation
D. Canary release with production monitoring

<details>
<summary>Show answer</summary>

**Correct answer: D.** Shift-right validates behavior after release, in production and with real traffic; a monitored canary is a clear example. Unit tests, requirement reviews, and test data preparation are earlier, shift-left activities.

</details>

#### MCQ 29. How does DevOps most change the QA role?

A. QA builds quality into automated pipelines and uses production evidence.
B. QA stops testing entirely.
C. QA only writes manual scripts.
D. QA becomes the release owner.

<details>
<summary>Show answer</summary>

**Correct answer: A.** DevOps moves QA toward automated regression, quality gates, and production observability rather than late manual gatekeeping. Option D overstates the change; release accountability usually remains with product and business owners.

</details>

#### MCQ 30. A feature is deployed behind an off flag and enabled for 5% of users. What is the difference between deployment and release here?

A. Deployment and release are the same event.
B. Release happened before deployment.
C. Deployment moved the code; release makes it available to users.
D. The feature was never tested.

<details>
<summary>Show answer</summary>

**Correct answer: C.** Deployment places the artifacts in the environment, while release makes the functionality available to users; the flag decouples the two. Option A ignores the flag, and option B reverses the order.

</details>

## Part 2 — Test Levels and Testing Types (60 questions)

### Test levels

#### MCQ 31. What is the main purpose of unit testing?

A. Verify end-to-end business workflows
B. Verify individual functions or components in isolation
C. Verify production monitoring
D. Verify user acceptance

<details>
<summary>Show answer</summary>

**Correct answer: B.** Unit testing isolates the smallest testable pieces of code, such as functions or components, and checks their logic directly. End-to-end workflows belong to system or acceptance testing, not unit tests.

</details>

#### MCQ 32. Who typically owns unit tests?

A. The Product Owner
B. The release manager
C. The developers
D. End users

<details>
<summary>Show answer</summary>

**Correct answer: C.** Developers write and own unit tests because they know the implementation and can run them continuously. QA may set expectations for coverage, but does not replace developer ownership.

</details>

#### MCQ 33. Integration testing primarily verifies what?

A. Interfaces and data flow between components
B. Individual statements within a function
C. Market fit of the product
D. Production capacity

<details>
<summary>Show answer</summary>

**Correct answer: A.** Integration testing checks that components communicate correctly and pass data as expected. Testing individual statements is unit testing, while market fit and capacity belong to other activities.

</details>

#### MCQ 34. In top-down integration, what stands in for lower layers that are not ready?

A. Drivers
B. Production data
C. Feature flags
D. Stubs

<details>
<summary>Show answer</summary>

**Correct answer: D.** Top-down integration starts with high-level components and uses stubs to simulate lower layers. Drivers are the opposite pattern, used in bottom-up integration to call higher-level components.

</details>

#### MCQ 35. In bottom-up integration, what stands in for higher layers?

A. Stubs
B. Drivers
C. Canary nodes
D. Database replicas

<details>
<summary>Show answer</summary>

**Correct answer: B.** Bottom-up integration starts with low-level components and uses drivers to invoke them as if the higher layers existed. Stubs are used in top-down integration.

</details>

#### MCQ 36. Big-bang integration is best described as:

A. Combining all components at once
B. Adding components one at a time with stubs
C. Testing only interfaces
D. Releasing to all users

<details>
<summary>Show answer</summary>

**Correct answer: A.** Big-bang integration brings every component together in one step. Adding components gradually is incremental integration, which is a different strategy.

</details>

#### MCQ 37. Which is a risk of big-bang integration?

A. Too many stubs
B. Too much early isolation
C. Failures are hard to isolate
D. It cannot test interfaces

<details>
<summary>Show answer</summary>

**Correct answer: C.** When everything is integrated at once, a failure could come from any interface or component, making diagnosis slow. The problem is not too much isolation; it is too little.

</details>

#### MCQ 38. System testing is performed against what?

A. Individual functions
B. Component interfaces only
C. The source code
D. End-to-end requirements in a production-like environment

<details>
<summary>Show answer</summary>

**Correct answer: D.** System testing evaluates the complete, integrated product against its requirements in an environment that resembles production. Unit and integration testing cover smaller scopes.

</details>

#### MCQ 39. What is the main goal of acceptance testing?

A. Judge whether the product meets business and user needs for release
B. Find code-level defects
C. Measure server throughput
D. Verify unit coverage

<details>
<summary>Show answer</summary>

**Correct answer: A.** Acceptance testing decides whether the product is acceptable to its business and users and can be released. Finding code defects and measuring throughput are lower-level or non-functional concerns.

</details>

#### MCQ 40. UAT is typically performed by:

A. Developers
B. Real users or business representatives
C. The Scrum Master
D. Database administrators

<details>
<summary>Show answer</summary>

**Correct answer: B.** User acceptance testing uses real users or business representatives to validate end-to-end business workflows. Developers and administrators may support it, but they are not the acceptance authority.

</details>

#### MCQ 41. Alpha testing is:

A. External users in production
B. Automated unit testing
C. A performance test
D. Internal, controlled testing before external release

<details>
<summary>Show answer</summary>

**Correct answer: D.** Alpha testing happens internally and under controlled conditions before the product goes to external users. External real-world testing is beta testing.

</details>

#### MCQ 42. Beta testing is:

A. Internal developer testing
B. A code review
C. A limited external release to real users for feedback
D. A regression suite

<details>
<summary>Show answer</summary>

**Correct answer: C.** Beta testing releases a limited version to real users in real environments and collects feedback before general availability. Internal controlled testing is alpha testing.

</details>

### Functional vs non-functional

#### MCQ 43. Functional testing answers which question?

A. How fast is it?
B. Does it do the right thing?
C. Is it secure?
D. Is it usable?

<details>
<summary>Show answer</summary>

**Correct answer: B.** Functional testing checks behavior against requirements and business rules. Speed, security, and usability are non-functional qualities.

</details>

#### MCQ 44. Non-functional testing focuses on:

A. How well the system behaves
B. Whether business rules are implemented
C. Whether requirements exist
D. Code style

<details>
<summary>Show answer</summary>

**Correct answer: A.** Non-functional testing evaluates qualities such as performance, security, reliability, and usability. Whether the business rules work is functional testing.

### Smoke testing

#### MCQ 45. Smoke testing is best described as:

A. A deep test of every requirement
B. A load test
C. A code review
D. A shallow, broad check that the build is stable enough for deeper testing

<details>
<summary>Show answer</summary>

**Correct answer: D.** Smoke testing checks a few critical paths to decide whether a build is worth testing in depth. It is intentionally shallow and broad, not exhaustive.

</details>

#### MCQ 46. When is smoke testing usually run?

A. Only before a major release
B. After every production incident
C. On every new build, before deeper suites
D. Only during UAT

<details>
<summary>Show answer</summary>

**Correct answer: C.** Smoke tests run on each new build so an unstable build is rejected before expensive regression work. Waiting until a major release leaves the team discovering basic breakage too late.

</details>

#### MCQ 47. What should happen when smoke testing fails?

A. The build is rejected and returned to development
B. Proceed with full regression anyway
C. Release with a warning
D. Skip testing

<details>
<summary>Show answer</summary>

**Correct answer: A.** A failed smoke test means the build is not stable enough for deeper testing, so it should go back to development. Running the full suite or releasing anyway wastes time and increases risk.

</details>

#### MCQ 48. Which is the broader build-acceptance check: smoke testing or build verification testing?

A. Smoke testing
B. Build verification testing
C. Regression testing
D. UAT

<details>
<summary>Show answer</summary>

**Correct answer: B.** Build verification testing is the broader check that the build is complete, deployable, configured, and functional at its core. Smoke testing is usually the fast critical-path subset.

</details>

### Sanity testing

#### MCQ 49. Sanity testing is:

A. A broad critical-path check on a new build
B. A full regression cycle
C. A narrow check after a small change to confirm it is worth fuller testing
D. A performance baseline

<details>
<summary>Show answer</summary>

**Correct answer: C.** Sanity testing is narrow and change-focused, confirming that a small fix is stable enough for broader tests. A broad new-build check is smoke testing.

</details>

#### MCQ 50. When is sanity testing most useful?

A. On a brand-new build with no changes
B. Before requirements are written
C. During production monitoring
D. After a small fix to confirm the affected area works

<details>
<summary>Show answer</summary>

**Correct answer: D.** Sanity testing follows a small change or fix to verify the affected area before spending time on full regression. It is not a new-build gate or a production monitoring activity.

</details>

#### MCQ 51. What is the key difference between smoke and sanity testing?

A. Smoke is narrow, and sanity is broad.
B. Smoke is broad build acceptance, and sanity is narrow and change-focused.
C. They are identical.
D. Sanity is only automated.

<details>
<summary>Show answer</summary>

**Correct answer: B.** Smoke testing checks critical paths across a new build, while sanity testing focuses narrowly on a specific change. Option A reverses the two.

</details>

### Regression testing

#### MCQ 52. Regression testing is:

A. Retesting the exact defect that was fixed
B. Testing only new features
C. Measuring performance
D. Re-running tests to ensure changes did not break existing behavior

<details>
<summary>Show answer</summary>

**Correct answer: D.** Regression testing protects existing behavior from side effects of change. Retesting the exact defect is confirmation testing, and testing only new features is not regression.

</details>

#### MCQ 53. When should regression testing run?

A. After code, dependency, configuration, or environment changes
B. Only once per year
C. Only before the first release
D. Only when tests fail

<details>
<summary>Show answer</summary>

**Correct answer: A.** Regression is driven by change, including code, dependencies, configuration, and environment. A fixed annual or first-release schedule misses the changes that create risk.

</details>

#### MCQ 54. Which is the best basis for selecting regression tests under time pressure?

A. Alphabetical order
B. The oldest test cases
C. Risk: changed areas, integrations, high-traffic paths, defect history
D. Random sampling

<details>
<summary>Show answer</summary>

**Correct answer: C.** Risk-based selection targets the areas most likely to break and most costly if they do. Alphabetical order, age, and random sampling ignore both impact and change.

</details>

#### MCQ 55. Regression testing differs from retesting because:

A. Regression protects existing behavior, while retesting confirms a specific fix.
B. Regression is only manual.
C. Retesting is broader.
D. They are the same.

<details>
<summary>Show answer</summary>

**Correct answer: A.** Retesting is narrow and defect-driven; regression is broad and change-driven. Option C reverses their scope.

</details>

#### MCQ 56. A fix passes its original failing test. What else should be done?

A. Nothing; close the defect.
B. Only update the test case.
C. Release immediately.
D. Run targeted regression around the affected area and related cases.

<details>
<summary>Show answer</summary>

**Correct answer: D.** Passing the original test proves the reported path is fixed, not that nearby behavior is intact. Targeted regression and related cases catch side effects before release.

</details>

### Retesting and confirmation

#### MCQ 57. Retesting is also called:

A. Regression testing
B. Confirmation testing
C. Exploratory testing
D. Load testing

<details>
<summary>Show answer</summary>

**Correct answer: B.** Retesting confirms that a specific defect is fixed, so it is also called confirmation testing. Regression testing checks the wider product instead.

</details>

#### MCQ 58. What should retesting include beyond the original failing scenario?

A. Only the exact original steps
B. No additional checks
C. Related boundary, negative, and nearby workflow cases
D. A full performance test

<details>
<summary>Show answer</summary>

**Correct answer: C.** A fix can resolve one path and disturb related boundaries or workflows, so retesting should extend slightly beyond the original steps. Only repeating the original case risks closing the defect too early.

</details>

### Build verification

#### MCQ 59. Build verification testing primarily confirms:

A. Every requirement works
B. Performance targets are met
C. Security is airtight
D. The build is complete, deployable, and its core functions work

<details>
<summary>Show answer</summary>

**Correct answer: D.** Build verification testing is a build-acceptance gate: the build is complete, deployable, correctly configured, and functional at its core. Full requirement, performance, and security validation happen in deeper testing.

</details>

### Performance testing family

#### MCQ 60. Performance testing is the umbrella for:

A. Speed, responsiveness, stability, and resource use under workload
B. Only UI rendering
C. Only security
D. Only unit tests

<details>
<summary>Show answer</summary>

**Correct answer: A.** Performance testing evaluates how the system behaves under load, including speed, stability, and resource consumption. Load, stress, spike, soak, volume, and scalability testing are its specialized forms.

</details>

#### MCQ 61. Load testing applies:

A. Sudden extreme spikes
B. Sustained load for days
C. Expected or peak workload
D. Large data volumes without users

<details>
<summary>Show answer</summary>

**Correct answer: C.** Load testing uses the expected or peak workload the business anticipates, with a realistic user mix. Sudden extremes are spike testing, long durations are soak testing, and large data volumes are volume testing.

</details>

#### MCQ 62. Stress testing is designed to:

A. Measure expected peak
B. Find the breaking point and observe failure behavior
C. Validate usability
D. Verify backups

<details>
<summary>Show answer</summary>

**Correct answer: B.** Stress testing exceeds expected capacity to find where the system breaks and how it behaves afterward. Measuring expected peak is load testing.

</details>

#### MCQ 63. Spike testing focuses on:

A. Long-duration stability
B. Data volume
C. Expected user mix
D. Sudden sharp load increases and recovery

<details>
<summary>Show answer</summary>

**Correct answer: D.** Spike testing applies a sudden, sharp load change to test elasticity, queuing, and recovery. Long-duration stability belongs to soak testing.

</details>

#### MCQ 64. Soak testing is also known as:

A. Endurance testing
B. Smoke testing
C. Sanity testing
D. Acceptance testing

<details>
<summary>Show answer</summary>

**Correct answer: A.** Soak testing runs a sustained load for a long period to check endurance and stability over time. It is unrelated to smoke or sanity testing.

</details>

#### MCQ 65. Soak testing is most likely to reveal:

A. Immediate crashes at peak
B. Memory leaks and gradual resource exhaustion
C. Translation errors
D. Broken links

<details>
<summary>Show answer</summary>

**Correct answer: B.** Problems that accumulate slowly, such as memory leaks, resource exhaustion, and log growth, appear during long runs. Immediate peak failures are more typical of stress or spike tests.

</details>

#### MCQ 66. Volume testing stresses:

A. User concurrency
B. Network latency
C. Large amounts of data
D. Accessibility

<details>
<summary>Show answer</summary>

**Correct answer: C.** Volume testing uses large databases, files, or queues to check data handling and storage limits. User concurrency is the load axis, not the volume axis.

</details>

#### MCQ 67. Scalability testing checks:

A. Whether adding resources maintains performance under growth
B. Whether the UI is responsive
C. Whether defects are fixed
