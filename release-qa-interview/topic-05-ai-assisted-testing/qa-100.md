# Release QA Interview Practice — Topic 5

100 open questions on AI-assisted programming and testing for release QA.
Answers are hidden so you can attempt each question first. The focus is Claude
Code and MCP, with the vocabulary and examples from
`using-ai-from-zero-to-claude-code.md` and `mcp-demo/`. No AI session, test, or
MCP call was executed for this bank; treat every example as a teaching artifact.

## Part 1 — AI and LLM Foundations for QA (8 questions)

#### Q1. What does an LLM do, and why is it not a database?

<details>
<summary>Show answer</summary>

An LLM predicts the next token from patterns learned during training, conditioned on the prompt and context. It does not look up a stored row or guarantee a correct fact. That makes it useful for drafting, summarizing, and generating options, but every output still needs verification.

</details>

#### Q2. What is a token, and what is a context window?

<details>
<summary>Show answer</summary>

A token is a piece of text the model reads or writes; a word may be one or several tokens. The context window is the total token budget for the instructions, files, conversation, and output. More context is not automatically better, because irrelevant material can hide the detail that matters.

</details>

#### Q3. Why does a model's training cutoff matter to release QA?

<details>
<summary>Show answer</summary>

The model may not know a recent library version, CLI flag, browser behavior, or vendor limit. A version-sensitive answer can be stale even when it sounds confident. Check the current documentation or the repository before using the claim in a release decision.

</details>

#### Q4. What is non-determinism, and why does it matter for reproducibility?

<details>
<summary>Show answer</summary>

The same prompt can produce different wording, test ideas, or fixes on another run. That is useful for brainstorming but weak for evidence. Capture the prompt, model, files, command, and output when a result must be repeated or defended.

</details>

#### Q5. What is a hallucination? Give a QA example.

<details>
<summary>Show answer</summary>

A hallucination is a confident output that is not true, such as inventing an API, a CLI flag, a test result, or a stack trace. A QA example is an assistant claiming a test passed when it never ran, or proposing `pytest --fix-flaky` when no such flag exists. The output looks plausible, which is why it must be checked.

</details>

#### Q6. Why is a confident answer not evidence?

<details>
<summary>Show answer</summary>

Confidence is a property of the generated text, not of the world. The model can be fluent and wrong at the same time. Evidence is a command, a diff, a log, a test report, or a source you can inspect and reproduce.

</details>

#### Q7. Where can AI help most in release QA?

<details>
<summary>Show answer</summary>

It is strongest at breadth and drafting: turning requirements into risks, suggesting edge cases, summarizing a long failure log, reviewing a diff, drafting a bug report, and proposing regression checks. It is weakest at knowing your product rules and at proving that something actually works.

</details>

#### Q8. What should a QA engineer never delegate to an AI?

<details>
<summary>Show answer</summary>

Never delegate the release decision, the final diagnosis, or the claim that a test passed. Those require human judgment and observed evidence. AI can prepare the material for the decision, but a named reviewer remains accountable.

</details>

## Part 2 — Prompting and Context (9 questions)

#### Q9. What makes a prompt reviewable?

<details>
<summary>Show answer</summary>

A reviewable prompt names the task, the material, the constraints, the deliverable, and the evidence required. It also states what is out of scope and what “done” means. A reviewer should be able to see why each part of the answer was requested.

</details>

#### Q10. Rewrite “Write tests for the quiz” as a stronger prompt.

<details>
<summary>Show answer</summary>

A stronger version names the files and behavior: “Read `quiz.html`, `cards.md`, and `flashcards.py`. Do not edit. Propose a test checklist for one-card-at-a-time, Show answer, and Next card. Cover empty data, malformed cards, keyboard use, and refresh. Mark assumptions. Return Area, Risk, Test idea, Expected result, and Evidence.” It is bounded and reviewable.

</details>

#### Q11. Why specify constraints and acceptance criteria?

<details>
<summary>Show answer</summary>

Without constraints the model invents scope, format, and product rules. Acceptance criteria tell it what must be true before the answer is acceptable: a table shape, a required evidence column, no edits, or a test that must pass. They make the answer easier to reject when it is wrong.

</details>

#### Q12. How do file references and `@` help?

<details>
<summary>Show answer</summary>

They point the model at the exact file or directory instead of asking it to guess. In Claude Code, `@path` includes a file or directory in context. The smallest relevant set is usually better than dumping the whole repository.

</details>

#### Q13. How should you iterate on an AI answer?

<details>
<summary>Show answer</summary>

Ask for a plan or assumptions first, review it, then narrow to one change or one test. Show the actual output when something fails, and ask for the smallest fix. Review the diff before running anything, then run the check yourself.

</details>

#### Q14. What is prompt injection?

<details>
<summary>Show answer</summary>

Prompt injection is an instruction hidden in content the model reads, such as a file, web page, ticket, log line, or MCP tool result. It tries to make the model follow the data as if it were a user command. It is not solved by a magic phrase in the prompt.

</details>

#### Q15. How do you defend against prompt injection?

<details>
<summary>Show answer</summary>

Treat tool and file output as data, give the assistant the least privilege it needs, keep secrets out of context, require approval for destructive or network actions, and review the tool call as well as the final answer. Scoped tools and human review reduce the risk more than prompt wording does.

</details>

#### Q16. What should you do when the model asks for more context?

<details>
<summary>Show answer</summary>

Give it the smallest artifact that answers the question: the failing test, the relevant function, the requirement, or the log window. Do not paste the whole repository or production data. If the request is vague, ask the model to state which decision the missing context would change.

</details>

#### Q17. How do you prompt for assumptions and unknowns?

<details>
<summary>Show answer</summary>

Ask directly: “List the product rules you cannot verify, the assumptions you are making, and the evidence you would need.” Then review that list. An answer that separates facts from assumptions is easier to trust than one that presents everything as certain.

</details>

## Part 3 — AI-Assisted Test Design and Test Data (12 questions)

#### Q18. How do you turn a requirement into risks before writing test cases?

<details>
<summary>Show answer</summary>

State the behavior, then ask for risks by category: data, state, input, integration, non-functional, and release. For each risk, ask for a test idea and the evidence that would prove it. Choose the risks that matter before generating cases.

</details>

#### Q19. How can AI help generate edge cases?

<details>
<summary>Show answer</summary>

Ask it to enumerate empty, single, many, duplicate, malformed, long, special-character, interrupted, and repeated-input cases. Then remove the ones that do not apply to the product. The model widens the list; you decide which cases are real risks.

</details>

#### Q20. What are equivalence partitions?

<details>
<summary>Show answer</summary>

Equivalence partitions group inputs that should behave the same way, so one representative test covers the group. For card count, the groups might be zero, one, several, and the maximum. Boundary values test the edges between groups.

</details>

#### Q21. What boundary values would you test for the quiz's card count?

<details>
<summary>Show answer</summary>

Zero cards, one card, two cards, the maximum supported count, and one above the maximum if the product defines it. Also test the first card, the last card, and the transition after the last card. The empty set and the single-card set often expose different bugs.

</details>

#### Q22. What is an exploratory charter, and how can AI help?

<details>
<summary>Show answer</summary>

A charter gives an exploratory session a target and a time box, such as “explore refresh and keyboard navigation for 20 minutes.” AI can suggest charters and heuristics, but a human runs the session and records what actually happened.

</details>

#### Q23. How should AI be used to create synthetic test data?

<details>
<summary>Show answer</summary>

Ask for realistic but invented data, with the awkward cases included: empty fields, long text, Unicode, duplicates, and malformed records. Keep the set small and label it synthetic. Never seed the prompt with production user data.

</details>

#### Q24. What data must not go into a test-data prompt?

<details>
<summary>Show answer</summary>

Real customer data, personal information, credentials, tokens, private keys, and unredacted production logs. If the case truly needs production-shaped data, use an approved environment and redact or synthesize it first.

</details>

#### Q25. Why label synthetic data?

<details>
<summary>Show answer</summary>

A reviewer must be able to tell invented rows from real records. A label such as `SYNTHETIC` in the fixture or file name prevents accidental use in a demo or a report. It also makes cleanup and provenance clear.

</details>

#### Q26. What coverage gaps can AI not fill?

<details>
<summary>Show answer</summary>

It does not know the product's real rules, supported environments, user behavior, production data distribution, release risk appetite, or whether a test is flaky in CI. Those come from the product, logs, analytics, and the team.

</details>

#### Q27. How do you review an AI-generated test checklist?

<details>
<summary>Show answer</summary>

Check that every case traces to a risk, has an expected result, and names the evidence. Remove invented product rules, duplicates, and cases that cannot be executed. Add the non-functional and accessibility cases the model missed.

</details>

#### Q28. How can AI help with regression test ideas?

<details>
<summary>Show answer</summary>

Give it the diff and the test inventory, and ask what changed, what depends on the change, what failed before, and what the release cannot afford to break. Treat the output as candidates; apply the team's risk rules and keep the set explainable.

</details>

#### Q29. What is the risk of asking for “as many tests as possible”?

<details>
<summary>Show answer</summary>

The model will produce volume, including duplicates, untestable cases, and cases built on invented rules. A long list feels thorough but can hide the missing high-risk test. Ask for prioritized risks and evidence instead.

</details>

## Part 4 — AI-Assisted Debugging and Code Review (10 questions)

#### Q30. What should you include when giving a stack trace to an AI assistant?

<details>
<summary>Show answer</summary>

Include the full trace, the command or action, the first error, the environment and version, recent changes, the relevant log window with secrets removed, and the expected versus actual behavior. A truncated trace often hides the cause.

</details>

#### Q31. Why ask for hypotheses instead of a verdict?

<details>
<summary>Show answer</summary>

A single verdict anchors the investigation on the model's first guess. Ranked hypotheses with supporting evidence and a next check keep the human in control and make it easier to eliminate a wrong path.

</details>

#### Q32. How do you reproduce a failure before accepting a fix?

<details>
<summary>Show answer</summary>

Write the shortest steps, record expected and actual behavior, run them on the same build and environment, capture the evidence, and repeat once to check determinism. A fix is not accepted until the original reproduction no longer fails.

</details>

#### Q33. What should a diff-review prompt ask for?

<details>
<summary>Show answer</summary>

Ask for behavior changes, missing or weakened tests, error handling, unrelated edits, secrets or debug output, dependency/configuration changes, and rollback risk. Require file:line references and a separate list of claims the reviewer cannot verify from the diff.

</details>

#### Q34. What is the difference between a suggested test and evidence?

<details>
<summary>Show answer</summary>

A suggested test is a plan: “a test for empty cards would cover this.” Evidence is a result: “I ran this command and it passed; here is the output.” Never report the first as the second.

</details>

#### Q35. What three regression rings do you check for a bug fix?

<details>
<summary>Show answer</summary>

The same failure no longer reproduces; adjacent behavior and the previous data format still work; and the change can be rolled back without leaving data or configuration broken. A fix that passes only the new test is not enough.

</details>

#### Q36. How do you review an AI-proposed fix?

<details>
<summary>Show answer</summary>

Read the diff for scope and behavior changes, confirm the test actually exercises the failure, run the test and the nearby suite, and check the rollback. Ask what the fix does not change, and look for tests that were weakened to make the change pass.

</details>

#### Q37. What is anchoring bias in AI-assisted debugging?

<details>
<summary>Show answer</summary>

Anchoring is accepting the first plausible diagnosis and interpreting later evidence through it. Asking for ranked hypotheses, evidence for each, and a falsifying check reduces it. The human should be willing to discard the first answer.

</details>

#### Q38. What does “what evidence would change my mind?” accomplish?

<details>
<summary>Show answer</summary>

It turns a claim into a testable prediction. If the model cannot name the observation that would prove it wrong, the claim is probably not ready for a release decision. It also gives you the next experiment.

</details>

#### Q39. How do you report an AI-assisted bug finding?

<details>
<summary>Show answer</summary>

Report the reproduction, expected and actual behavior, environment, frequency, and the evidence you captured. State what the AI suggested and what you verified separately. The report should stand without the AI transcript.

</details>

## Part 5 — Claude Code Essentials (10 questions)

#### Q40. How is Claude Code different from an autocomplete plugin?

<details>
<summary>Show answer</summary>

Claude Code is an agent that can read files, search the repository, edit files, and run commands, subject to permissions. An autocomplete plugin suggests the next line inside an editor. With Claude Code, the important questions are what task you delegated, what it changed, and how you verified it.

</details>

#### Q41. What is `CLAUDE.md`?

<details>
<summary>Show answer</summary>

`CLAUDE.md` is a Markdown file of project instructions loaded at the start of a Claude Code session. It holds commands, conventions, source-of-truth files, and the definition of done. It is context, not enforcement, and it is not a place for secrets.

</details>

#### Q42. What belongs in a project `CLAUDE.md`?

<details>
<summary>Show answer</summary>

Include how to run the tests, the files and formats that are authoritative, what not to edit, dependency rules, and what “done” means. Keep it concrete and verifiable. Move path-specific rules into narrower rule files instead of growing the main file.

</details>

#### Q43. Why keep `CLAUDE.md` short?

<details>
<summary>Show answer</summary>

It is loaded every session and re-injected after compaction, so it competes with the task for context. A long file is less likely to be followed consistently. The handbook recommends keeping it under 200 lines and updating it when the same mistake repeats.

</details>

#### Q44. How do you manage context in Claude Code?

<details>
<summary>Show answer</summary>

Point at the smallest useful set of files, use `@path` references when you need specific files, and avoid dumping the whole repository. Keep the task focused, summarize long investigations, and start a fresh session when the task changes. Context is finite, and irrelevant material can hide the relevant line.

</details>

#### Q45. Why start a fresh session instead of continuing a long one?

<details>
<summary>Show answer</summary>

A long session contains old assumptions, tool output, and abandoned paths that can distract the model. A fresh session with the finding, the relevant files, and the current question is often cheaper and more accurate. Summarize what matters before you restart.

</details>

#### Q46. What do permission modes control?

<details>
<summary>Show answer</summary>

They control what Claude Code may do without asking: read-only actions, file edits, command execution, and broader automation. The safest QA default is read-only first, review every write, and approve commands narrowly. Never bypass permissions on a machine or folder you care about.

</details>

#### Q47. Why is least privilege important for an AI coding agent?

<details>
<summary>Show answer</summary>

An agent with broad file, shell, and network access can make a small mistake into a large one. Least privilege limits the blast radius: a reviewer gets read-only tools, a test runner gets a narrow command, and secrets stay out of reach. It also makes the agent's actions easier to review.

</details>

#### Q48. What is plan mode used for?

<details>
<summary>Show answer</summary>

Plan mode lets the agent research and propose a change without editing files. It is useful when the task is ambiguous, the change touches shared fixtures, or you want to review the strategy before any write. You approve the plan before switching to implementation.

</details>

#### Q49. How do you review an AI-assisted change before accepting it?

<details>
<summary>Show answer</summary>

Review the diff for scope and behavior changes, confirm the tests exercise the change, check for secrets or unrelated edits, and verify the rollback. Commit a working state first so git is the reliable undo. A passing test alone does not prove the change is safe.

</details>

## Part 6 — Skills and Reusable Workflows (9 questions)

#### Q50. What is a skill?

<details>
<summary>Show answer</summary>

A skill is a reusable instruction package, usually a folder with a `SKILL.md` file and optional references or scripts. It can be invoked explicitly by name or matched automatically from its description. A skill turns a good prompt into a repeatable workflow.

</details>

#### Q51. How do skills differ from slash commands?

<details>
<summary>Show answer</summary>

Older custom slash commands live in `.claude/commands/`; current Claude Code documentation treats commands as a form of skill and recommends `.claude/skills/` for new work. Skills use the same idea but can be invoked automatically and can carry supporting files. Use skills for new reusable workflows.

</details>

#### Q52. What frontmatter fields does a `SKILL.md` use?

<details>
<summary>Show answer</summary>

Useful fields include `name`, `description`, `argument-hint`, `allowed-tools`, `disable-model-invocation`, `context: fork`, and `model`. The description is the automatic trigger, and `disable-model-invocation: true` protects side-effecting skills. Keep the body focused and put long references in sibling files.

</details>

#### Q53. What is progressive disclosure for skills?

<details>
<summary>Show answer</summary>

At session start, Claude Code sees only the skill's name and description. When the skill is invoked, it loads the `SKILL.md` body; reference files load only if the body points to them. This keeps a large checklist or example set out of every session.

</details>

#### Q54. What is the difference between explicit and automatic skill invocation?

<details>
<summary>Show answer</summary>

Explicit invocation is typing `/skill-name` with optional arguments. Automatic invocation is Claude Code matching the task against the skill's description and choosing the skill. A vague description makes automatic invocation unreliable.

</details>

#### Q55. How do you write a good skill description?

<details>
<summary>Show answer</summary>

Say what the skill does and when to use it, with the trigger words a user would actually say. “Turn a requirement into a risk-based QA checklist; use when the user asks for test risks, a test plan, or a release checklist” is stronger than “makes checklists.” Keep it specific and honest about scope.

</details>

#### Q56. What is a good first QA skill?

<details>
<summary>Show answer</summary>

A risk-checklist skill: read a requirement, separate facts from assumptions, group risks by data/state/input/integration/release, and produce a table with test idea, expected result, evidence, and priority. It is bounded, reusable, and easy to review. It does not edit files or claim a test passed.

</details>

#### Q57. Why use `disable-model-invocation: true`?

<details>
<summary>Show answer</summary>

It prevents the model from invoking a skill automatically, so only a human can run it. Use it for skills with side effects, such as committing, deploying, deleting data, or changing shared configuration. The skill can still be invoked explicitly when the human intends it.

</details>

#### Q58. How do you test and maintain a skill?

<details>
<summary>Show answer</summary>

Run it on a real requirement, inspect the output against the rules, and fix the skill when it misses or invents something. Version the skill with the project and review changes like code. A stale skill is a stale process, not a one-off bad answer.

</details>

## Part 7 — Subagents and Agent Workflows (9 questions)

#### Q59. What is a subagent?

<details>
<summary>Show answer</summary>

A subagent is a separate Claude instance with its own context window and system prompt, defined by a Markdown file such as `.claude/agents/test-plan-reviewer.md`. The main agent delegates a task and receives a summary. The subagent does not automatically see the main conversation.

</details>

#### Q60. Why is context isolation useful?

<details>
<summary>Show answer</summary>

A subagent can review a large test plan, search a big repository, or inspect many logs without filling the main session. It returns a compact report instead of all the raw material. The cost is that it must read the source itself, so give it exact paths.

</details>

#### Q61. What tools should a reviewer subagent have?

<details>
<summary>Show answer</summary>

A reviewer usually needs `Read` and `Grep`, not edit or shell access. Read-only tools prevent it from “fixing” the thing it is reviewing. If it needs to run a focused test, give it a narrow command allowlist rather than broad shell access.

</details>

#### Q62. When should you run subagents in parallel?

<details>
<summary>Show answer</summary>

Run them in parallel when the tasks are independent: correctness review, security review, test coverage, and documentation review of the same diff. Do not run parallel writers on the same files or tasks that depend on one another's intermediate result. Collect the reports before deciding.

</details>

#### Q63. What is the implementer/reviewer pattern?

<details>
<summary>Show answer</summary>

One agent implements a small change, and a separate read-only agent reviews the brief, the diff, and the tests. The reviewer does not see the implementer's private reasoning, which reduces rubber-stamping. The controller decides what to fix and whether the result is acceptable.

</details>

#### Q64. What are the main orchestration risks with subagents?

<details>
<summary>Show answer</summary>

Duplicated work, stale context, conflicting edits, cost, and lost reasoning when the subagent returns. A fresh context may miss project conventions or a recent change. Clear briefs, disjoint file ownership, and a controller that keeps the plan reduce the risk.

</details>

#### Q65. When should you not use a subagent?

<details>
<summary>Show answer</summary>

Do not use one for a one-line lookup, a task that needs the full main conversation, or a write that must be coordinated with another writer. The overhead of a fresh context is not worth it for trivial work. Do it directly.

</details>

#### Q66. Give a release-QA use for a subagent.

<details>
<summary>Show answer</summary>

Use a read-only subagent to review a test plan for missing risks and evidence, audit a diff for missing tests, or search the repository for every use of a risky fixture. Give it exact paths and a structured output format. The main agent acts on the report.

</details>

#### Q67. How do you brief a subagent?

<details>
<summary>Show answer</summary>

Give it the task, the exact files, the question, the output format, and the permission boundaries. Do not paste the whole conversation. State what it must not do, such as editing files. Ask for file:line evidence and a clear verdict.

</details>
