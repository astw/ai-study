## Part 1 — Relational Basics (7 questions)

#### Q1. What is the difference between a table, a row, and a column?

<details>
<summary>Show answer</summary>

A table is a named relation for one kind of thing, such as `users`; a row is one record, such as one user; and a column is one attribute, such as `email`. The column list is fixed by the schema, while rows are added and removed as data changes. A query returns a result set with the same table shape: named columns and rows.

</details>

#### Q2. What is a primary key, and what rules does the database enforce on it?

<details>
<summary>Show answer</summary>

A primary key is a column, or a combination of columns, that uniquely identifies each row. The database enforces two rules: no two rows may share the key value, and the key may not be `NULL`. In the flashcards schema every table has a single-column primary key: `user_id`, `deck_id`, `card_id`, and `review_id`.

</details>

#### Q3. What is a foreign key, and what does it guarantee?

<details>
<summary>Show answer</summary>

A foreign key is a column that refers to a primary key or unique key in another table, and the database enforces that the referenced row exists. For example, `decks.user_id` may contain only a value that appears in `users.user_id`, so a deck cannot belong to a user who does not exist. A foreign key prevents orphan rows, but it is not a uniqueness rule, and SQL Server does not automatically create an index for it.

</details>

#### Q4. What does `NULL` mean, and why is `NULL = NULL` not TRUE?

<details>
<summary>Show answer</summary>

`NULL` marks a missing or unknown value; it is not zero, not an empty string, and not equal to itself. Because there is no value to compare, `NULL = NULL` evaluates to UNKNOWN, and `WHERE` keeps only rows whose condition is TRUE. That is why a missing value is tested with `IS NULL` or `IS NOT NULL`, never with `= NULL`. In the sample rows, user 3 has a `NULL` display name and reviews 10003 and 10007 have `NULL` ratings.

</details>

#### Q5. How do the schema's data types differ between SQL Server and standard SQL?

<details>
<summary>Show answer</summary>

Whole numbers are `INT` in SQL Server and `INTEGER` in standard SQL, short text is `NVARCHAR(n)` versus `VARCHAR(n)`, and booleans are `BIT` versus `BOOLEAN`. The timestamp types differ in more than name: the schema uses `DATETIME2` on SQL Server and `TIMESTAMP` in standard SQL, where `TIMESTAMP` is a date and time. On SQL Server, `TIMESTAMP` is a synonym for `ROWVERSION`, a binary change-tracking value, so a SQL Server `TIMESTAMP` column is not a date at all. `NVARCHAR` stores Unicode text, and a length such as `NVARCHAR(255)` is a maximum, not a promise that the value fills it.

</details>

#### Q6. What is a one-to-many relationship, and on which side does the foreign key sit?

<details>
<summary>Show answer</summary>

A one-to-many relationship is one parent row with zero or more child rows, such as one user owning many decks. The foreign key sits on the many side, `decks.user_id`, and points at the primary key `users.user_id` on the one side. The same shape repeats in `cards.deck_id`, `reviews.card_id`, and `reviews.user_id`, and the sample rows show the many side with user 1 owning two decks and deck 101 holding two cards. Storing a list of deck IDs inside a user row would repeat data, be hard to search, and could not be checked by a foreign key.

</details>

#### Q7. You are handed this schema before a migration. How do you read it to find what identifies a row, what may be missing, and what could become orphaned?

<details>
<summary>Show answer</summary>

Read the primary keys first: `user_id`, `deck_id`, `card_id`, and `review_id` each identify one row, so they are the keys a row count or a duplicate check should group on. Then read nullability: only `users.display_name` and `reviews.rating` allow `NULL`, which is why those two columns get their own missing-value checks. Finally read the foreign keys — `decks.user_id`, `cards.deck_id`, `reviews.card_id`, and `reviews.user_id` — because those are the relationships an import can break, and check `ck_reviews_rating` for the 1-to-5 rule on a non-null rating.

</details>

## Part 2 — Reading Data with SELECT (9 questions)

#### Q8. What do `SELECT` and `FROM` do, and in what order does the server process a query?

<details>
<summary>Show answer</summary>

`SELECT` lists the columns to return, and `FROM` names the table they come from. The server processes the query logically in the order `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, then `ORDER BY`, even though `SELECT` is written first. That order explains why a column alias created in `SELECT` cannot be used in `WHERE`: the alias does not exist yet when `WHERE` runs.

</details>

#### Q9. What is a column alias, and where can it be used?

<details>
<summary>Show answer</summary>

An alias renames a column in the result set, and `AS` makes the intent explicit: `LEN(front) AS front_length` is clearer than leaving the server to name the expression. An alias is usable in `ORDER BY` but not in `WHERE`, `GROUP BY`, or `HAVING`, because those clauses run before the `SELECT` list is computed. An explicit alias also gives an exported CSV or a test comparison a stable name that does not change between dialects or versions.

</details>

#### Q10. What does `DISTINCT` remove, and why is it a weak duplicate check?

<details>
<summary>Show answer</summary>

`DISTINCT` removes duplicate rows from the result, and it compares the whole selected row, not just the first column. `SELECT DISTINCT display_name FROM users` returns four rows including `NULL`, because users 1 and 4 share the name Alice and the missing name counts as one distinct value. That makes `DISTINCT` a poor duplicate check: a release check that asks how many times a value appears should use `GROUP BY` with `COUNT(*)`, which reports the count instead of hiding it.

</details>

#### Q11. Why does `ORDER BY` matter for a reproducible test result, and what does `DESC` do?

<details>
<summary>Show answer</summary>

Without `ORDER BY`, the server may return rows in any order, and the same query can produce a different order after statistics, indexes, or the plan change. `ORDER BY deck_id ASC, created_at DESC` sorts by deck ascending and, within each deck, by newest card first, and `ASC` is the default. When rows can tie on the last sort key, add a unique tiebreaker such as `card_id`, or their relative order is still not guaranteed.

</details>

#### Q12. How do you return the three newest cards in SQL Server?

<details>
<summary>Show answer</summary>

**SQL Server:**

```sql
SELECT TOP (3) card_id, front
FROM cards
ORDER BY created_at DESC;
```

The query returns the three newest cards: 1005, 1004, and 1003. `TOP` belongs in the `SELECT` list, and without `ORDER BY` it returns an arbitrary set of rows rather than a stable selection. Ties in the last sort key can still change which rows fall inside the limit, so add a unique tiebreaker when the sample must be reproducible.

</details>

#### Q13. How do you skip rows and return a page with `OFFSET ... FETCH NEXT`?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT card_id, front
FROM cards
ORDER BY created_at ASC
OFFSET 2 ROWS FETCH NEXT 2 ROWS ONLY;
```

This skips the two oldest cards, 1001 and 1002, and returns the next two, 1003 and 1004. SQL Server requires an `ORDER BY` for this form, and `OFFSET ... FETCH NEXT` is also standard SQL, so it is the portable paging choice. Add a unique tiebreaker such as `card_id`, or a tie at the page boundary can move a row between pages.

</details>

#### Q14. What is the standard SQL form for returning the first two cards?

<details>
<summary>Show answer</summary>

**Standard SQL:**

```sql
SELECT card_id, front
FROM cards
ORDER BY created_at ASC
FETCH FIRST 2 ROWS ONLY;
```

This returns the two oldest cards, 1001 and 1002. Standard SQL has no `TOP`; the limit is written after `ORDER BY` as `FETCH FIRST n ROWS ONLY`. `FETCH FIRST` runs without `ORDER BY` in some databases, but the rows it picks are then arbitrary, so keep the `ORDER BY` when the result feeds a test.

</details>

#### Q15. How do expressions behave with `NULL`, and how does concatenation differ between the dialects?

<details>
<summary>Show answer</summary>

Arithmetic with `NULL` produces `NULL`, so `rating * 2` is `NULL` for reviews 10003 and 10007 rather than zero. For text, SQL Server concatenates with `+` or the `CONCAT` function, while standard SQL uses `||`. `CONCAT` is the exception that treats a `NULL` argument as an empty string, whereas `+` and `||` return `NULL` when either operand is `NULL`, so user 3 gets a label with an empty name part from `CONCAT` and a `NULL` label from the other forms.

</details>

#### Q16. Why is `SELECT *` risky in a release check, and when is it acceptable?

<details>
<summary>Show answer</summary>

`SELECT *` returns whatever columns the table has at the moment, so a release that adds a column changes the result shape and can break a test that compares column counts or an export that expects fixed columns. Name the columns you need in any query that another person or system consumes. `SELECT *` is acceptable only for a quick look in a scratch database where the result shape is not part of the evidence.

</details>

## Part 3 — Filtering and NULL (11 questions)

#### Q17. What does `WHERE` do, and when does it run?

<details>
<summary>Show answer</summary>

`WHERE` evaluates a condition once per row and keeps only the rows whose condition is TRUE; FALSE and UNKNOWN both remove the row. It runs after `FROM` and before `GROUP BY`, so it filters individual rows before any grouping or aggregation. That is why a condition on a single row belongs in `WHERE`, while a condition on a total belongs in `HAVING`.

</details>

#### Q18. How does operator precedence affect a filter that mixes `AND` and `OR`?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT review_id, card_id, rating
FROM reviews
WHERE card_id = 1001 OR card_id = 1002 AND rating = 5;
```

**SQL Server and standard SQL:**

```sql
SELECT review_id, card_id, rating
FROM reviews
WHERE (card_id = 1001 OR card_id = 1002)
  AND rating = 5;
```

`AND` binds tighter than `OR`, so the first filter means "card 1001, or card 1002 with rating 5", and it returns reviews 10001 and 10002. The second filter adds parentheses, so both conditions apply to both cards, and it returns review 10001 only. Precedence is fixed by the language rather than by the order in which the clauses were typed, so parentheses are how a mixed filter states its intent.

</details>

#### Q19. What does `IN` do, and how does it relate to a chain of `OR` comparisons?

<details>
<summary>Show answer</summary>

`IN` tests a column against a list and is shorthand for a chain of `OR` equalities, so `card_id IN (1001, 1004)` matches the same rows as `card_id = 1001 OR card_id = 1004`. On the sample reviews it returns 10001, 10002, 10005, and 10007. `IN` uses the same equality rules as `=`, so a `NULL` anywhere in the list makes the negated `NOT IN` form return no rows.

</details>

#### Q20. Is `BETWEEN` inclusive, and what is the trap with date/time columns?

<details>
<summary>Show answer</summary>

`BETWEEN a AND b` means `>= a AND <= b`, so both endpoints are included, and `rating BETWEEN 2 AND 4` returns reviews 10002, 10004, and 10006. On a date/time column, SQL Server's `BETWEEN '2026-01-20' AND '2026-01-25'` stops at midnight at the start of January 25 and silently drops anything recorded later that day, such as review 10006 at 14:00. Write the window as a half-open range instead — SQL Server `>= '2026-01-20' AND < '2026-01-26'`, standard SQL `>= TIMESTAMP '2026-01-20 00:00:00' AND < TIMESTAMP '2026-01-26 00:00:00'` — when the requirement is "through January 25", so the boundary is explicit.

</details>

#### Q21. What do `%` and `_` mean in a `LIKE` pattern?

<details>
<summary>Show answer</summary>

In a `LIKE` pattern, `%` matches any run of zero or more characters and `_` matches exactly one character, so `front LIKE 'What is%'` matches all five sample cards. A pattern such as `email LIKE '____@example.com'` matches only the two addresses with exactly four characters before the `@`, namely `dave@example.com` and `erin@example.com`. A pattern that starts with `%` can match anywhere and is expensive on a large table, and whether matching ignores case depends on the column's collation.

</details>

#### Q22. How do you test for a missing value, and what does `= NULL` return?

<details>
<summary>Show answer</summary>

The test for a missing value is `IS NULL` or `IS NOT NULL`; these are predicates that always return TRUE or FALSE, never UNKNOWN. `WHERE display_name = NULL` returns no rows, not even user 3, because `NULL = NULL` is UNKNOWN for every row. `WHERE display_name IS NULL` returns user 3, the one row whose name is missing.

</details>

#### Q23. What is three-valued logic, and how does `WHERE` treat UNKNOWN?

<details>
<summary>Show answer</summary>

SQL conditions have three possible outcomes — TRUE, FALSE, and UNKNOWN — and a comparison involving `NULL` is UNKNOWN because there is no value to compare. `WHERE` keeps a row only when its condition is TRUE, so both FALSE and UNKNOWN remove the row. This is why `rating > 3` and `rating <= 3` do not add up to `COUNT(*)`: reviews 10003 and 10007 are UNKNOWN and disappear from both filters.

</details>

#### Q24. Why can `NOT IN` with a `NULL` in the list return zero rows?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT card_id
FROM cards
WHERE card_id NOT IN (1001, NULL);
```

This returns zero rows: the predicate expands to `card_id <> 1001 AND card_id <> NULL`, the second comparison is UNKNOWN, and `TRUE AND UNKNOWN` is UNKNOWN, so no row passes. The same trap appears when the list comes from a subquery over a nullable column: `rating NOT IN (SELECT rating FROM reviews WHERE user_id = 1)` returns zero rows even though reviews 10002 and 10006 look like the expected answer, because user 1's ratings include a `NULL`. Fix it by adding `rating IS NOT NULL` to the subquery or by rewriting the check with `NOT EXISTS`.

</details>

#### Q25. What does `COALESCE` do, and how does it differ from SQL Server's `ISNULL`?

<details>
<summary>Show answer</summary>

`COALESCE(a, b, ...)` returns its first argument that is not `NULL`, so `COALESCE(display_name, '(no name)')` shows `(no name)` for user 3 and the stored name for every other user. It is standard SQL and accepts any number of arguments, while SQL Server's `ISNULL` takes exactly two arguments and is not standard SQL. Neither function is the same as the predicate `IS NULL`, which tests for a missing value rather than replacing one.

</details>

#### Q26. What does `NULLIF` do, and why is it useful in an average calculation?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT CAST(SUM(rating) AS DECIMAL(10, 2))
       / NULLIF(COUNT(rating), 0) AS avg_rating
FROM reviews;
```

`NULLIF(a, b)` returns `NULL` when `a` equals `b`, and `a` otherwise, so `NULLIF(COUNT(rating), 0)` turns a zero denominator into `NULL` instead of letting the division fail. On the sample rows the expression returns 3.8, because 19 is divided by the 5 rated reviews rather than all 7. Without the decimal cast, `SUM(rating) / NULLIF(COUNT(rating), 0)` would perform integer division and return 3.

</details>

#### Q27. How do you write a filter for rating-5 reviews written by user 1 or user 2, and why do the parentheses matter?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT review_id, user_id, rating
FROM reviews
WHERE (user_id = 1 OR user_id = 2)
  AND rating = 5;
```

This returns reviews 10001 and 10005, the two rating-5 reviews written by user 1 or user 2. Without the parentheses, `user_id = 1 OR user_id = 2 AND rating = 5` means every review by user 1, whatever its rating, plus rating-5 reviews by user 2, so the sample rows also return 10003, 10004, and 10007. The parentheses are the only way to say that the `OR` belongs inside the `AND`, because the server applies fixed precedence and will not infer intent.

</details>

## Part 4 — Aggregating and Grouping (11 questions)

#### Q28. What does `COUNT(*)` count, and why is it the safest baseline aggregate?

<details>
<summary>Show answer</summary>

`COUNT(*)` counts rows and does not look at column values, so a `NULL` in any column never reduces the count. On the sample data, `SELECT COUNT(*) FROM reviews` returns 7, and `SELECT COUNT(*) FROM reviews WHERE rating > 3` returns 3. It is the safest baseline aggregate because every row contributes exactly one, and it returns 0 rather than `NULL` when nothing matches.

</details>

#### Q29. What does `COUNT(column)` count, and how does it differ from `COUNT(*)`?

<details>
<summary>Show answer</summary>

`COUNT(column)` counts rows where that column is not `NULL`, so `COUNT(*)` and `COUNT(rating)` on `reviews` return 7 and 5. The difference, 2, is the number of unrated reviews 10003 and 10007, which makes the subtraction a quick audit of a nullable column. Unlike `COUNT(*)`, `COUNT(column)` treats a missing value as absent, so the two counts answer different questions.

</details>

#### Q30. What does `COUNT(DISTINCT column)` count, and how does it differ from `SELECT DISTINCT`?

<details>
<summary>Show answer</summary>

`COUNT(DISTINCT column)` counts distinct non-`NULL` values, so `COUNT(DISTINCT card_id)` on `reviews` returns 4 and `COUNT(DISTINCT display_name)` on `users` returns 3. `SELECT DISTINCT display_name` returns four rows including `NULL`, because `DISTINCT` keeps one row for the missing value. How many distinct values are stored and how many rows a deduplicated result has are therefore different numbers.

</details>

#### Q31. How do `SUM` and `AVG` treat `NULL`, and why is the average rating 3.8?

<details>
<summary>Show answer</summary>

`SUM` and `AVG` ignore `NULL` inputs, so the five non-null sample ratings add up to 19 and the two `NULL` ratings contribute nothing. `AVG(rating)` is 19 / 5 = 3.8, not 19 / 7, because the denominator is the count of rated reviews. On SQL Server, `AVG` over an `INT` column returns an `INT` and discards the fraction, so cast to `DECIMAL` to see 3.8 instead of 3.

</details>

#### Q32. What do `MIN` and `MAX` return, including on text and dates?

<details>
<summary>Show answer</summary>

`MIN` and `MAX` return the smallest and largest value in a column, and they work on text and dates as well as numbers. On `cards`, `MIN(created_at)` and `MAX(created_at)` give a quick first-and-last-record check, and on `reviews` the rating range is 2 to 5. Like the other value aggregates they ignore `NULL`, so an empty or all-`NULL` input returns `NULL`.

</details>

#### Q33. What does `GROUP BY` do, and what does grouping `cards` by `deck_id` return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT deck_id, COUNT(*) AS card_count
FROM cards
GROUP BY deck_id;
```

`GROUP BY` divides the rows into groups that share the same values in the listed columns and evaluates the aggregate once per group. The query returns three rows: deck 101 with 2 cards, deck 102 with 1, and deck 103 with 2. Deck 104 does not appear because `GROUP BY` groups only the rows that exist; it does not invent an empty group.

</details>

#### Q34. What does `HAVING` do, and what does `HAVING COUNT(*) > 1` keep?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT deck_id, COUNT(*) AS card_count
FROM cards
GROUP BY deck_id
HAVING COUNT(*) > 1;
```

`HAVING` filters groups after aggregation, so it is the clause for a condition on a total such as `COUNT(*) > 1`. The query returns decks 101 and 103, the only decks with more than one card. An aggregate cannot appear in `WHERE`, because the groups do not exist yet when `WHERE` runs.

</details>

#### Q35. What is the difference between `WHERE` and `HAVING`?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT user_id, COUNT(*) AS good_reviews
FROM reviews
WHERE rating >= 4
GROUP BY user_id
HAVING COUNT(*) > 1;
```

`WHERE` filters individual rows before grouping, and `HAVING` filters groups after `GROUP BY`, so a row condition belongs in `WHERE` and a group condition belongs in `HAVING`. Here the `WHERE` removes the low and `NULL` ratings before grouping, leaving user 1 with one qualifying review and user 2 with two; the `HAVING` then removes user 1 and returns user 2. Moving `rating >= 4` into `HAVING` would make the query invalid, because `rating` is neither grouped nor aggregated.

</details>

#### Q36. How do the aggregates behave on an empty or all-`NULL` input?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT COUNT(*)   AS review_count,
       SUM(rating) AS rating_sum,
       AVG(rating) AS rating_avg
FROM reviews
WHERE 1 = 0;
```

`SUM`, `AVG`, `MIN`, and `MAX` ignore `NULL` inputs, and when no values remain they return `NULL`, not 0. The query returns one row containing 0, `NULL`, and `NULL`, because `COUNT` is the exception that returns 0 for an empty set. A report that must show a visible zero for a sum or average needs `COALESCE`, and an all-`NULL` average is a finding about the data rather than a rendering bug.

</details>

#### Q37. How does grouping by two columns work, and what does `GROUP BY user_id, rating` return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT user_id, rating, COUNT(*) AS review_count
FROM reviews
GROUP BY user_id, rating;
```

Grouping by two columns makes one group per distinct pair, and `NULL` forms its own group. The query returns six rows, including user 1 with a `NULL` rating and a count of 2 for the two unrated reviews. Every column in the `SELECT` list must appear in `GROUP BY` or be inside an aggregate, or SQL Server and standard SQL reject the query.

</details>

#### Q38. What does an aggregate query without `GROUP BY` return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT COUNT(*)                            AS review_count,
       SUM(rating)                         AS rating_sum,
       AVG(CAST(rating AS DECIMAL(10, 2))) AS rating_avg
FROM reviews;
```

An aggregate query with no `GROUP BY` treats the whole table as one group, so it returns exactly one row. The query returns 7, 19, and 3.8; with `WHERE 1 = 0` added it still returns one row, this time 0, `NULL`, and `NULL`. Because the single row survives an empty filter, `COUNT` is safe for a baseline, while `SUM` and `AVG` may return `NULL` that a report must handle.

</details>

## Part 5 — Joins and UNION (14 questions)

#### Q39. What is a join, and what do the left and right sides and the `ON` clause mean?

<details>
<summary>Show answer</summary>

A join combines rows from two tables through a relationship they share, such as `cards.deck_id = decks.deck_id`. In `FROM decks AS d INNER JOIN cards AS c`, `decks` is the left side and `cards` is the right side, and `ON` states the match rule; a row with no partner on the other side is **unmatched**. Join on the foreign-key pairs, not on text such as `title` or `display_name`, because users 1 and 4 share the name Alice and decks 101 and 103 share the title Biology 101.

</details>

#### Q40. What does `INNER JOIN` return, and how many rows does the deck-to-card inner join return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT d.deck_id, d.title, c.card_id, c.front
FROM decks AS d
INNER JOIN cards AS c ON c.deck_id = d.deck_id
ORDER BY d.deck_id, c.card_id;
```

`INNER JOIN` returns only rows that have a match on both sides, and an unmatched row from either table is dropped; `JOIN` on its own means `INNER JOIN`. The statement returns five rows, one per card — 1001 and 1002 under deck 101, 1003 under deck 102, and 1004 and 1005 under deck 103 — while deck 104, which has no cards, produces no row. The five rows equal `COUNT(*)` on `cards` only because every card has a deck: the join returns matched combinations, not a fixed number of either table's rows.

</details>

#### Q41. What does `LEFT JOIN` return, and how many rows does the deck-to-card left join return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT d.deck_id, d.title, c.card_id, c.front
FROM decks AS d
LEFT JOIN cards AS c ON c.deck_id = d.deck_id
ORDER BY d.deck_id, c.card_id;
```

`LEFT JOIN` preserves every row from the left table: a left row with matches produces one row per match, and a left row with no match produces one row with `NULL` in every column of the right table. The statement returns six rows — the five matched rows plus one row for deck 104 with `NULL` in `c.card_id`, `c.front`, and every other `cards` column. Standard SQL accepts `LEFT JOIN` and `LEFT OUTER JOIN`, and so does SQL Server.

</details>

#### Q42. How do you find rows with no match using `LEFT JOIN ... WHERE ... IS NULL`?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT d.deck_id, d.title
FROM decks AS d
LEFT JOIN cards AS c ON c.deck_id = d.deck_id
WHERE c.card_id IS NULL
ORDER BY d.deck_id;
```

This is an anti-join: the left join keeps every deck, and the `WHERE` keeps only the rows where the right side did not match. `c.card_id` is the primary key of `cards`, so a real card can never hold `NULL` there, and a `NULL` in the result can only mean "no card matched this deck"; the query returns deck 104, Empty Deck. The null test must name a `NOT NULL` key: testing `r.rating` on a users-to-reviews left join returns reviews 10003 and 10007, which belong to user 1 and carry no rating, alongside the users with no reviews.

</details>

#### Q43. What does `RIGHT JOIN` return, and how does `A RIGHT JOIN B` compare with `B LEFT JOIN A`?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT c.card_id, c.front, r.review_id, r.rating
FROM reviews AS r
RIGHT JOIN cards AS c ON c.card_id = r.card_id
ORDER BY c.card_id, r.review_id;
```

`RIGHT JOIN` preserves every row from the right table and null-extends the left columns when no row matches. The statement returns eight rows: all seven reviews, plus card 1005 with `NULL` in `r.review_id` and `r.rating` because it has no reviews. `A RIGHT JOIN B` returns exactly the same rows as `B LEFT JOIN A`, so the query is usually rewritten to start from `cards` and use `LEFT JOIN reviews`. Standard SQL and SQL Server both accept `RIGHT JOIN` and `RIGHT OUTER JOIN`.

</details>

#### Q44. What does `FULL OUTER JOIN` preserve, and how many rows does the users-to-decks full join return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT u.user_id, u.display_name, d.deck_id, d.title
FROM users AS u
FULL OUTER JOIN decks AS d ON d.user_id = u.user_id
ORDER BY u.user_id, d.deck_id;
```

`FULL OUTER JOIN` preserves unmatched rows from both sides: a match produces one row, and an unmatched row appears once with `NULL`s in the other table's columns. The statement returns six rows — four matches (user 1 with decks 101 and 102, user 2 with deck 103, and user 3 with deck 104) and two unmatched users, 4 and 5, with `NULL` deck columns. No deck is unmatched, because the foreign key guarantees that every deck names an existing user. Both SQL Server and standard SQL accept `FULL OUTER JOIN`.

</details>

#### Q45. What is a self join, and why does it need two aliases and a key inequality?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT a.deck_id,
       a.card_id AS card_a,
       b.card_id AS card_b
FROM cards AS a
INNER JOIN cards AS b ON b.deck_id = a.deck_id
                     AND b.card_id > a.card_id
ORDER BY a.deck_id, a.card_id, b.card_id;
```

A self join joins a table to itself by giving it two different aliases and comparing rows of that table with other rows of the same table; the aliases are required, or the second reference is ambiguous. The strict inequality `b.card_id > a.card_id` stops a card from pairing with itself and keeps each unordered pair once, so deck 101 returns `(1001, 1002)` instead of four rows. The query returns two rows — `(101, 1001, 1002)` and `(103, 1004, 1005)` — because deck 102 holds only one card and produces no pair.

</details>

#### Q46. How does a join chain work, and how many rows does users → decks → cards → reviews return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT u.user_id, d.deck_id, c.card_id, r.review_id
FROM users AS u
INNER JOIN decks   AS d ON d.user_id = u.user_id
INNER JOIN cards   AS c ON c.deck_id = d.deck_id
INNER JOIN reviews AS r ON r.card_id = c.card_id
ORDER BY u.user_id, d.deck_id, c.card_id, r.review_id;
```

A join chain adds one table at a time, with each `ON` connecting the new table to a table already in the query, and the finest table sets the row count. The statement returns seven rows, one per review: five for user 1 and two for user 2. Parents with no child anywhere below them drop out — users 4 and 5 have no decks, user 3's deck 104 has no cards, and card 1005 has no reviews.

</details>

#### Q47. What is the difference between `ON` and `USING`, and does SQL Server support `USING`?

<details>
<summary>Show answer</summary>

**SQL Server:**

```sql
SELECT d.deck_id, d.title, c.card_id
FROM decks AS d
INNER JOIN cards AS c ON c.deck_id = d.deck_id;
```

**Standard SQL:**

```sql
SELECT deck_id, title, card_id
FROM decks AS d
INNER JOIN cards AS c USING (deck_id);
```

`ON` names the key comparison explicitly and is the only form SQL Server accepts, while `USING` is a standard SQL shorthand for the case where both tables give the key column the same name. Both statements return the same five rows, but `USING` merges the join column into one output column, so `deck_id` is unambiguous without a qualifier, whereas with `ON` it must be qualified as `d.deck_id` or `c.deck_id`. `USING` is a syntax error in SQL Server, and it requires the two key columns to have identical names, so when the names differ only `ON` works.

</details>

#### Q48. How does filter placement in `ON` versus `WHERE` change a left join?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT d.deck_id, c.card_id
FROM decks AS d
LEFT JOIN cards AS c ON c.deck_id = d.deck_id
                    AND c.front LIKE 'What is D%'
ORDER BY d.deck_id, c.card_id;
```

**SQL Server and standard SQL:**

```sql
SELECT d.deck_id, c.card_id
FROM decks AS d
LEFT JOIN cards AS c ON c.deck_id = d.deck_id
WHERE c.front LIKE 'What is D%'
ORDER BY d.deck_id, c.card_id;
```

`ON` controls which rows count as a match, and `WHERE` controls which rows survive after the join. In the first statement the extra `ON` condition does not remove a deck: a card that fails it becomes unmatched, so the query returns all four decks, with `NULL` card columns for 102, 103, and 104 and only card 1002 matching "What is D%". In the second statement the `WHERE` removes the `NULL`-extended rows and turns the left join back into an inner join, returning just card 1002 and its deck. In an inner join the two placements are equivalent, but in an outer join they are not.

</details>

#### Q49. How does a one-to-many join multiply rows, and why does `COUNT(*)` return 5 for the deck-to-card join?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT COUNT(*)                  AS joined_rows,
       COUNT(DISTINCT d.deck_id) AS decks,
       COUNT(DISTINCT c.card_id) AS cards
FROM decks AS d
INNER JOIN cards AS c ON c.deck_id = d.deck_id;
```

Each join repeats a parent row once per matching child, so a count taken after the join counts combinations rather than entities. The statement returns 5, 3, and 5: five joined rows, three decks that have at least one card, and five cards, because deck 101 contributes two rows. A report that asked "how many decks have content?" and used `COUNT(*)` would answer 5, which is wrong; `COUNT(DISTINCT key)` recovers the entity count, though it does not repair a duplicated `SUM`.

</details>

#### Q50. What is the difference between `UNION` and `UNION ALL`, and how many rows does each return for the deck and review user IDs?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT user_id FROM decks
UNION
SELECT user_id FROM reviews
ORDER BY user_id;
```

`UNION` stacks the rows of two result sets and removes duplicate rows from the combined result, while `UNION ALL` keeps every row. The `UNION` statement returns three rows — user IDs 1, 2, and 3 — because values repeated inside each branch collapse into one. Replacing `UNION` with `UNION ALL` returns eleven rows, four from `decks` and seven from `reviews`, including six 1s. Use `UNION` for a distinct value list and `UNION ALL` for reconciliation counts, where duplicates are the evidence.

</details>

#### Q51. What must two `UNION` branches have in common, and which branch supplies the result's column names?

<details>
<summary>Show answer</summary>

Both branches must return the same number of columns, with a compatible type in each position, and the columns line up by position rather than by name. The result takes its column names from the first branch: if the second selects `card_id` where the first selects `deck_id`, both values stack under the name `deck_id`, and the server cannot check that the two names mean the same thing. When the types differ, the server applies its conversion rules by position, so a value may convert silently or fail when it does not parse; select matching types deliberately instead of relying on that. The rules are the same in SQL Server and in standard SQL.

</details>

#### Q52. How does `UNION` decide which rows are duplicates, and how does it treat `NULL`?

<details>
<summary>Show answer</summary>

`UNION` compares the whole selected row, not just the first column, and removes rows that are equal in every position. For that comparison, `NULL` counts as equal to `NULL`, so two all-`NULL` rows collapse into one, unlike a `WHERE` comparison where `NULL = NULL` is UNKNOWN. `UNION ALL` performs no comparison and returns every row from both branches. Duplicate removal requires the server to sort or hash the combined rows, which is why `UNION` costs more than `UNION ALL`.

</details>

## Part 6 — Subqueries and Simple CTEs (9 questions)

#### Q53. What is a scalar subquery, and what happens when it returns more than one row or no rows?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT review_id, rating
FROM reviews
WHERE rating > (
    SELECT AVG(CAST(rating AS DECIMAL(10, 2)))
    FROM reviews
);
```

A scalar subquery returns exactly one column and at most one row, so it can be used anywhere a single value is allowed — a comparison, the `SELECT` list, or the right-hand side of `SET` in an `UPDATE`. If the subquery returns more than one row the statement fails, and if it returns no row the value is `NULL`, which can silently turn a comparison into UNKNOWN. The query returns reviews 10001, 10002, and 10005: the subquery returns 3.8, the average of the five non-null ratings, and the two `NULL` ratings fail the outer comparison rather than participating in it.

</details>

#### Q54. How does `IN (subquery)` work, and which decks does it return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT deck_id, title
FROM decks
WHERE deck_id IN (
    SELECT deck_id
    FROM cards
);
```

`IN (subquery)` is a membership test: the outer value must equal one of the values the subquery returns. The subquery must return exactly one column but may return any number of rows, and duplicates in that list do not duplicate the outer rows. The statement returns decks 101, 102, and 103; deck 104 is absent because no card names it, even though the inner list is 101, 101, 102, 103, 103.

</details>

#### Q55. How does `EXISTS (subquery)` work, and why is `SELECT 1` the usual inner select list?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT d.deck_id, d.title
FROM decks AS d
WHERE EXISTS (
    SELECT 1
    FROM cards AS c
    WHERE c.deck_id = d.deck_id
);
```

`EXISTS (subquery)` is an existence test: TRUE when the subquery returns at least one row and FALSE when it returns none. The inner query refers to `d.deck_id` from the outer row, so it is a correlated subquery that the server evaluates per deck; the statement returns decks 101, 102, and 103, and a deck with several cards still produces one outer row. The select list of an `EXISTS` subquery is ignored, which is why `SELECT 1` is the conventional choice: it states that only the existence of a row matters.

</details>

#### Q56. How does `NOT EXISTS` find a deck with no cards, and why is it safer than `NOT IN`?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT d.deck_id, d.title
FROM decks AS d
WHERE NOT EXISTS (
    SELECT 1
    FROM cards AS c
    WHERE c.deck_id = d.deck_id
);
```

`NOT EXISTS` is TRUE when the inner query returns no row, so the statement returns deck 104, Empty Deck, and never duplicates an outer row. A `NULL` inside the inner comparison is UNKNOWN and does not count as a match, so `NOT EXISTS` stays TRUE for a deck that truly has no cards, which makes it the safe form for absence checks. The equivalent `NOT IN` query returns the same row here only because `cards.deck_id` is `NOT NULL`; if the subquery returned a `NULL`, `NOT IN` would return zero rows and turn a real finding into a false clean result.

</details>

#### Q57. What is a correlated subquery, and how does it find the latest review per card?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
SELECT r.review_id, r.card_id, r.rating, r.reviewed_at
FROM reviews AS r
WHERE r.reviewed_at = (
    SELECT MAX(r2.reviewed_at)
    FROM reviews AS r2
    WHERE r2.card_id = r.card_id
)
ORDER BY r.card_id, r.review_id;
```

A correlated subquery references a column from the outer query, so its result can differ for every outer row. The mental model is: for each outer row, run the inner query with that row's values. The statement returns four rows — 10002 for card 1001, 10006 for card 1002, 10004 for card 1003, and 10007 for card 1004 — each the latest review for its card. Review 10007 shows that the latest review does not need a rating, because the test filters on time; card 1005 has no reviews and does not appear. If two reviews tie for the latest timestamp, both survive, so add a unique tiebreaker or `ROW_NUMBER` when the check expects exactly one row.

</details>

#### Q58. What is a simple CTE, and what does the deck card count CTE return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
WITH deck_card_counts AS (
    SELECT deck_id, COUNT(*) AS card_count
    FROM cards
    GROUP BY deck_id
)
SELECT d.title, COALESCE(c.card_count, 0) AS card_count
FROM decks AS d
LEFT JOIN deck_card_counts AS c ON c.deck_id = d.deck_id;
```

A simple CTE gives a name to a subquery and places it before the statement that uses it, in the shape `WITH name AS (query)` followed by the main statement. The CTE returns 101 → 2, 102 → 1, and 103 → 2; the `LEFT JOIN` from `decks` keeps deck 104, and `COALESCE` turns its missing count into 0, so the statement returns four rows. Two rows show Biology 101 because decks 101 and 103 share the title, and only the title is selected, so those rows cannot be told apart. The statement is standard SQL as well, though SQL Server requires the statement before `WITH` to end with a semicolon.

</details>

#### Q59. How do multiple CTEs in one `WITH` clause work, and what does the two-CTE deck report return?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql
WITH card_counts AS (
    SELECT deck_id, COUNT(*) AS card_count
    FROM cards
    GROUP BY deck_id
),
review_counts AS (
    SELECT c.deck_id, COUNT(*) AS review_count
    FROM cards AS c
    INNER JOIN reviews AS r ON r.card_id = c.card_id
    GROUP BY c.deck_id
)
SELECT d.deck_id,
       d.title,
       COALESCE(cc.card_count, 0) AS card_count,
       COALESCE(rc.review_count, 0) AS review_count
FROM decks AS d
LEFT JOIN card_counts   AS cc ON cc.deck_id = d.deck_id
LEFT JOIN review_counts AS rc ON rc.deck_id = d.deck_id
ORDER BY d.deck_id;
```

A single `WITH` clause may define several CTEs separated by commas; later definitions can refer to earlier ones, and the main statement can use any of them. The report returns four rows — 101 with 2 cards and 4 reviews, 102 with 1 and 1, 103 with 2 and 2, and 104 with 0 and 0 — because each CTE returns at most one row per deck, so neither left join can multiply the other. This is the pre-aggregate-then-join shape from Part 5 with names instead of nested tables.

</details>

#### Q60. When should you use a CTE versus a nested subquery?

<details>
<summary>Show answer</summary>

A CTE and a nested derived table answer the same question with the same result; the nested form puts the intermediate query inside `FROM` and needs an alias, while the CTE puts it before the statement under a name. The CTE's real gain is readability and reuse: the main statement can reference the name more than once, and the name says what the intermediate rows mean. A CTE is not a materialized result — SQL Server generally expands it into the statement, so referencing it twice can evaluate it twice, and a CTE alone is not a performance improvement. Use a nested subquery for a short, single-use intermediate and a CTE when a check has several named steps.

</details>

#### Q61. What is the scope of a CTE, and can a later statement reuse it?

<details>
<summary>Show answer</summary>

A CTE lives for exactly one statement: it can be used anywhere in the statement that follows it, including more than once, and the name is gone when that statement ends. The next statement cannot reference it, even in the same batch, so a result that must feed a second check needs the statement rerun or the result stored. In SQL Server the statement before a `WITH` must end with a semicolon; a missing terminator produces a syntax error near `with` that points at the wrong statement. A CTE is a naming device, not a temp table: it stores no rows, has no index or statistics of its own, and has no life beyond its statement.

</details>

#### Q62. How do you insert one row with `INSERT INTO ... VALUES`, and why should the column list be explicit?

#### Q64. What does `UPDATE` do, and why is an `UPDATE` without `WHERE` dangerous?

<details>
<summary>Show answer</summary>

**SQL Server and standard SQL:**

```sql

SET rating = 5
WHERE review_id = 10002;
```

`UPDATE table SET column = value WHERE condition` changes the matching rows; the `WHERE` uses the same rules as a `SELECT` filter, and without it every row matches. The statement changes review 10002 from 4 to 5 and affects one row. Removing the `WHERE` sets all seven reviews to 5, including the two `NULL` ratings, and destroys the original distribution; under autocommit the change is permanent, with no statement-level undo. #### Q65. How do you write an `UPDATE` whose rows come from a subquery?

The subquery supplies the row set: it returns the card IDs for the selected parent, and `IN` matches the reviews that name one of them. #### Q66. What does `DELETE` do, and what does `DELETE FROM reviews WHERE rating IS NULL` remove?

#### Q67. How do you delete rows chosen by a subquery, and why must children be deleted before parents?

#### Q68. What is a transaction, and what do `COMMIT` and `ROLLBACK` do?

<details>
<summary>Show answer</summary>

**SQL Server:**

```sql
BEGIN TRANSACTION;

UPDATE reviews
SET rating = 5
WHERE review_id = 10002;

SELECT review_id, rating
FROM reviews
WHERE review_id = 10002;

ROLLBACK TRANSACTION;
```

**Standard SQL:**

```sql
START TRANSACTION;

UPDATE reviews
SET rating = 5
WHERE review_id = 10002;

ROLLBACK;
```

A transaction groups statements so they are saved or undone as a unit: `COMMIT` makes every change permanent, and `ROLLBACK` undoes every change back to the start of the transaction. The `SELECT` inside this transaction shows review 10002 with rating 5 because a transaction sees its own changes; after the `ROLLBACK` the review holds 4 again. Other sessions cannot see the uncommitted 5, and the open transaction can hold locks that block them, so keep transactions short and always close them. Standard SQL uses `START TRANSACTION` instead of SQL Server's `BEGIN TRANSACTION`.

</details>

#### Q69. What is a savepoint, and how does `ROLLBACK TO SAVEPOINT` differ from rolling back the whole transaction?

<details>
<summary>Show answer</summary>

**SQL Server:**

```sql
BEGIN TRANSACTION;

INSERT INTO users (user_id, email, display_name, created_at)
VALUES (6, 'frank@example.com', 'Frank', '2026-02-15 09:00:00');

SAVE TRANSACTION after_user_insert;

UPDATE decks
SET is_public = 1
WHERE deck_id = 104;

ROLLBACK TRANSACTION after_user_insert;

COMMIT TRANSACTION;
```

**Standard SQL:**

```sql
START TRANSACTION;

INSERT INTO users (user_id, email, display_name, created_at)
VALUES (6, 'frank@example.com', 'Frank', TIMESTAMP '2026-02-15 09:00:00');

SAVEPOINT after_user_insert;

UPDATE decks
SET is_public = TRUE
WHERE deck_id = 104;

ROLLBACK TO SAVEPOINT after_user_insert;

COMMIT;
```

A savepoint is a named marker inside a transaction; rolling back to it undoes only the work done after the marker, keeps earlier work, and leaves the transaction open. Here the deck 104 update is undone, so the deck is private again, while user 6 is kept by the final `COMMIT`; a plain `ROLLBACK` instead would remove user 6 too. SQL Server writes `SAVE TRANSACTION name` and `ROLLBACK TRANSACTION name`, and it has no `RELEASE SAVEPOINT`, while standard SQL writes `SAVEPOINT name` and `ROLLBACK TO SAVEPOINT name`. A savepoint is not a commit: the transaction still needs its own `COMMIT` or `ROLLBACK`.

</details>

#### Q70. How do you set up and clean up test data without leaving fixtures behind?

## Part 8 — Schema, Constraints, Indexes, and Views (9 questions)

#### Q71. What does `CREATE TABLE` do, and what does the `reviews` definition declare?

<details>
<summary>Show answer</summary>

**SQL Server:**

```sql
CREATE TABLE reviews (
    review_id   INT PRIMARY KEY,
    card_id     INT NOT NULL,
    user_id     INT NOT NULL,
    rating      INT,
    reviewed_at DATETIME2 NOT NULL,
    CONSTRAINT fk_reviews_card FOREIGN KEY (card_id) REFERENCES cards (card_id),
    CONSTRAINT fk_reviews_user FOREIGN KEY (user_id) REFERENCES users (user_id),
    CONSTRAINT ck_reviews_rating CHECK (rating BETWEEN 1 AND 5)
);
```

`CREATE TABLE` names a table and defines its columns, each with a name, a type, and any constraints; the finished definition is a contract that every later `INSERT` and `UPDATE` must satisfy. The statement declares a primary key on `review_id`, two foreign keys, a check on `rating`, and `NOT NULL` on `card_id`, `user_id`, and `reviewed_at`, leaving `rating` nullable. Name the constraints, because SQL Server reports the name when it rejects a row and a migration needs the name to drop or change the rule. A table can reference only a table that already exists, so the creation order is users, then decks, then cards, then reviews. Standard SQL uses `INTEGER`, `TIMESTAMP`, and the same constraint syntax.

</details>

#### Q72. Which key constraints does the `reviews` table declare, and what does each one reject?

<details>
<summary>Show answer</summary>

`review_id INT PRIMARY KEY` combines uniqueness and not-null, so a duplicate or a `NULL` `review_id` is rejected. The two foreign keys require `card_id` and `user_id` to name existing parent rows, so a review with card 9999 or user 99 is rejected, and the same constraints reject deleting a parent while its reviews remain. In SQL Server the primary key also creates a clustered unique index by default, while a foreign key creates no index at all, so a child-column lookup can scan `reviews` unless an index exists. These rules are standard SQL as well.

#### Q73. What does a `UNIQUE` constraint do, and how does SQL Server treat multiple `NULL`s in a unique column?

<details>
<summary>Show answer</summary>

**SQL Server:**

```sql
CREATE TABLE users (
    user_id      INT PRIMARY KEY,
    email        NVARCHAR(255) NOT NULL UNIQUE,
    display_name NVARCHAR(100),
    created_at   DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
```

A `UNIQUE` constraint rejects duplicate values in a column or in a combination of columns, which is what would turn the two `alice@example.com` rows of `legacy_users` into a rejected insert. SQL Server treats `NULL`s as equal for uniqueness, so a single-column unique constraint accepts at most one `NULL`, while standard SQL permits more than one because `NULL` is not equal to anything. The durable rule is to declare unique columns `NOT NULL`, as `users.email` is here. The column-level `UNIQUE` word is shorthand for a table-level unique constraint, and the syntax is standard SQL apart from the type names and `SYSUTCDATETIME()`.

</details>

#### Q74. What does `NOT NULL` enforce, and what happens when it is added to a column that already holds `NULL`s?

<details>
<summary>Show answer</summary>

`NOT NULL` requires a value: an `INSERT` that omits the nullable `display_name` stores `NULL` and succeeds, while omitting `email` or writing `NULL` to it is rejected. A column declared without `NOT NULL` is nullable by default. Adding `NOT NULL` to an existing column validates every existing row, so a table that already holds a `NULL` rejects the change until the data is fixed. That is why a migration tightens constraints after cleanup, and why the DDL step itself is part of the test: the failure is evidence about the data, not only about the script.

</details>

#### Q75. What do `CHECK` and `DEFAULT` do, and why does `ck_reviews_rating` accept a `NULL` rating?

<details>
<summary>Show answer</summary>

A `CHECK` constraint rejects a row only when its condition is FALSE, and a `DEFAULT` supplies a value when the `INSERT` omits the column. `ck_reviews_rating` allows a non-null rating between 1 and 5, but a `NULL` rating makes `NULL BETWEEN 1 AND 5` UNKNOWN, and the database accepts UNKNOWN as well as TRUE — which is why reviews 10003 and 10007 exist unrated. A default does not apply to an explicit `NULL`: a nullable column keeps the `NULL`, and a `NOT NULL` column rejects the statement. Both rules are standard SQL; the SQL Server default form is `DEFAULT SYSUTCDATETIME()`, and standard SQL writes `DEFAULT CURRENT_TIMESTAMP`.

</details>

#### Q76. What is a view, and what does `v_deck_card_counts` return?

<details>
<summary>Show answer</summary>

**SQL Server:**

```sql
CREATE OR ALTER VIEW v_deck_card_counts AS
SELECT d.deck_id,
       d.title,
       COUNT(c.card_id) AS card_count
FROM decks AS d
LEFT JOIN cards AS c ON c.deck_id = d.deck_id
GROUP BY d.deck_id, d.title;
```

A view is a named query stored in the database: it has a name and a column list, and each reference evaluates its definition against the current base tables, so it is not a copy of the rows. The view returns one row per deck — 101 with 2 cards, 102 with 1, 103 with 2, and 104 with 0 — because it starts from `decks` with a `LEFT JOIN` that keeps the empty deck. The count is `COUNT(c.card_id)`, not `COUNT(*)`, because the left join's `NULL`-extended row for deck 104 would make `COUNT(*)` report 1. The standard form replaces `CREATE OR ALTER VIEW` with `CREATE VIEW` and keeps the rest unchanged.

</details>

#### Q77. How does `CREATE OR ALTER VIEW` differ from `CREATE VIEW`, and what is the standard SQL form?

<details>
<summary>Show answer</summary>

`CREATE OR ALTER VIEW` creates a view or replaces an existing one in a single SQL Server statement, available from SQL Server 2016 SP1 onward; earlier versions create with `CREATE VIEW` and change with `ALTER VIEW`. Standard SQL defines a view with `CREATE VIEW` and has no "or alter" form, so replacing an existing definition is a product-specific operation there. In SQL Server, `CREATE VIEW` and `CREATE OR ALTER VIEW` must be the only statement in their batch, so a script creates the view first and queries it in a later batch. A `CREATE OR REPLACE VIEW` form exists in some products but is not standard SQL.

</details>

#### Q78. What is an index, and how do clustered and nonclustered indexes differ?

<details>
<summary>Show answer</summary>

**SQL Server:**

```sql
CREATE NONCLUSTERED INDEX ix_cards_deck_id
    ON cards (deck_id);
```

**Standard SQL:**

```sql
CREATE INDEX ix_cards_deck_id
    ON cards (deck_id);
```

An index is a derived structure kept beside a table so the database can find rows without reading every page; the table remains the source of truth and the optimizer may ignore the index. In SQL Server a clustered index defines the physical order of the rows — its leaf level is the data — so a table can have only one, and each primary key here creates one by default; a nonclustered index is a separate sorted structure with a pointer to the row, and a table can have many. A foreign key does not create an index, so `ix_cards_deck_id` supports both the cards-to-decks join and a parent-delete check. Index DDL is not standardized; the portable `CREATE INDEX` form has no `CLUSTERED` or `NONCLUSTERED` word, and the product's default index type applies.

</details>

#### Q79. What should a QA engineer remember about view behavior, including stored rows, performance, nesting, and `SELECT *`?

<details>
<summary>Show answer</summary>

A view stores no rows, only a definition and a column list, so querying the view reports new base rows without any change to the view itself. A view is not automatically faster: a view with a join and an aggregate does the same work as its base query, so do not treat it as a cache. Nested views hide logic, because each layer can filter, join, or collapse rows, so read every view in the chain before blaming the base table. In SQL Server, `SELECT *` inside a view is expanded when the view is created and that column list is stored, so name columns explicitly in a view that another system reads. A view with a `GROUP BY` is read-only, while a simple view without aggregation can be updatable and pass `INSERT`, `UPDATE`, or `DELETE` through to the base table.

</details>
