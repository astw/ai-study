## Part 1 — Relational Basics (10 questions)

#### MCQ 1. A migration adds 3,000 records to `reviews`. Which term names one of those records?

A. A column
B. A row
C. A table
D. A schema

<details>
<summary>Show answer</summary>

**Correct answer: B.** A row is one record, here one review. A column is one attribute shared by every record, a table is the named relation that holds the rows, and a schema is the overall database structure.

</details>

#### MCQ 2. A schema review asks what a primary key enforces. Which pair of rules does a primary key enforce?

A. Values may repeat when another column differs
B. One value may be `NULL` per table
C. Values are unique and never `NULL`
D. Values must match a foreign key in another table

<details>
<summary>Show answer</summary>

**Correct answer: C.** The primary key is unique and may not be `NULL`: no two rows share the key value and no key value is missing. A foreign key is the rule about matching another table, which is a different concept.

</details>

#### MCQ 3. A schema review finds `deck_1`, `deck_2`, and `deck_3` columns in a proposed `users` table. What design is better?

A. A second table with one row per deck and a `user_id` foreign key
B. A single text column holding a comma-separated list of decks
C. Three separate `users` tables, one per deck slot
D. A wider `users` table with `deck_4` reserved for growth

<details>
<summary>Show answer</summary>

**Correct answer: A.** A design that needs a new column for each new value usually needs a second table. One user can own many decks, so the decks table holds one row per deck with a `user_id` foreign key; a comma-separated list could not be checked by a foreign key.

</details>

#### MCQ 4. What does a foreign key guarantee about the child column?

A. Every value is unique across the child table
B. Every value is automatically indexed by SQL Server
C. Every value is `NOT NULL`
D. Every non-`NULL` value matches a row in the parent table

<details>
<summary>Show answer</summary>

**Correct answer: D.** The database enforces that the referenced parent row exists, so a non-`NULL` child value must match a parent key. A foreign key is not a uniqueness rule, and SQL Server does not index it automatically.

</details>

#### MCQ 5. A test inserts a deck with `user_id = 99`, and no user 99 exists. What does `fk_decks_user` do?

A. Creates user 99 with a placeholder email
B. Stores the deck with a `NULL` owner
C. Rejects the insert
D. Accepts the deck but hides it from joins

<details>
<summary>Show answer</summary>

**Correct answer: C.** `fk_decks_user` requires the referenced user row to exist, so the insert is rejected. The constraint cannot invent a user or null out a `NOT NULL` column.

</details>

#### MCQ 6. A tester reads the `reviews` DDL and looks for nullable columns. Which column permits `NULL`?

A. `review_id`
B. `card_id`
C. `reviewed_at`
D. `rating`

<details>
<summary>Show answer</summary>

**Correct answer: D.** Only `rating` is nullable in `reviews`; `review_id`, `card_id`, and `reviewed_at` are `NOT NULL`. The CHECK constraint still accepts a `NULL` rating because the condition is UNKNOWN for that row.

</details>

#### MCQ 7. A test checks how an unrated review stores its missing value. Which statement about `NULL` is correct?

A. It is a missing value, distinct from both 0 and an empty string
B. It is stored as 0 so arithmetic works
C. It is stored as an empty string in a numeric column
D. It equals itself, so `NULL = NULL` is TRUE

<details>
<summary>Show answer</summary>

**Correct answer: A.** `NULL` means a missing or unknown value. It is not 0 and not an empty string, and `NULL = NULL` is UNKNOWN rather than TRUE.

</details>

#### MCQ 8. A SQL Server column is declared `TIMESTAMP`. What does it actually hold?

A. The date and time of the row's last update
B. A `ROWVERSION` binary value for change tracking
C. A Unix epoch integer
D. A copy of the table's `created_at` value

<details>
<summary>Show answer</summary>

**Correct answer: B.** On SQL Server, `TIMESTAMP` is a synonym for `ROWVERSION`: an automatically generated binary value for change tracking, not a date. Standard SQL's `TIMESTAMP` is a date and time, which is why the schema uses `DATETIME2` on SQL Server.

</details>

#### MCQ 9. A tester finds user 1 owns two decks and user 5 owns none. Which relationship does the schema model?

A. One deck owns many users
B. Many users share one deck
C. Every user owns at least one deck
D. One user owns zero or more decks

<details>
<summary>Show answer</summary>

**Correct answer: D.** Each user owns zero or more decks, so user 1 shows the many side and user 5 shows that zero children are allowed. The foreign key sits on the decks side, pointing at `users`.

</details>

#### MCQ 10. A developer asks whether `cards` sits on the one side or the many side of the deck-to-card relationship. Which is correct for `cards.deck_id`?

A. The many side, pointing at the parent key
B. The one side, pointing at the child key
C. A junction table between decks and cards
D. Both sides, because the key is shared

<details>
<summary>Show answer</summary>

**Correct answer: A.** The foreign key sits on the many side: `cards.deck_id` points at `decks.deck_id`, and one deck can own many cards.

</details>

## Part 2 — Reading Data with SELECT (14 questions)

#### MCQ 11. Which clause names the table a query reads?

A. `SELECT`
B. `FROM`
C. `WHERE`
D. `ORDER BY`

<details>
<summary>Show answer</summary>

**Correct answer: B.** `FROM` names the table the rows come from; `SELECT` chooses the columns, `WHERE` filters rows, and `ORDER BY` sorts the result.

</details>

#### MCQ 12. A release adds a `phone_number` column to `users`. Which select list keeps a three-column export unchanged?

A. `SELECT *`
B. `SELECT users.*`
C. `SELECT user_id, email, display_name`
D. `SELECT COUNT(*)`

<details>
<summary>Show answer</summary>

**Correct answer: C.** An explicit column list is a contract: it keeps returning the same three columns when a later release adds a column. `SELECT *` would start returning four columns and could break a column-count comparison or an export.

</details>

#### MCQ 13. A select-list alias is available in which clause?

A. `ORDER BY`
B. `WHERE`
C. `GROUP BY`
D. `HAVING`

<details>
<summary>Show answer</summary>

**Correct answer: A.** `ORDER BY` is the only clause that can reference a select-list alias. `WHERE`, `GROUP BY`, and `HAVING` run before the `SELECT` list is computed, so the alias does not exist yet there.

</details>

#### MCQ 14. A tester runs `SELECT LEN(front) AS front_length FROM cards WHERE front_length > 20`. What happens?

A. It returns the cards whose `front` text is longer than 20 characters
B. It sorts the cards by the computed length
C. It fails because the alias is not visible in `WHERE`
D. It returns every card with a `NULL` length

<details>
<summary>Show answer</summary>

**Correct answer: C.** `WHERE` runs before the `SELECT` list, so the alias `front_length` does not exist when the filter is evaluated; SQL Server rejects the query. Repeat `LEN(front)` in `WHERE` or wrap the query in a subquery.

</details>

#### MCQ 15. A tester runs `SELECT DISTINCT display_name FROM users`. How many rows come back?

A. 2
B. 3
C. 5
D. 4

<details>
<summary>Show answer</summary>

**Correct answer: D.** Four rows: `NULL`, Alice, Bob, and Erin. Users 1 and 4 collapse into one Alice row, and the `NULL` counts as one distinct value.

</details>

#### MCQ 16. `SELECT DISTINCT deck_id, title FROM decks` keeps both Biology 101 rows. Why?

A. `DISTINCT` compares only the first column
B. The deck IDs differ, so the pairs differ
C. Titles are unique in the `decks` table
D. `DISTINCT` never removes rows that contain text

<details>
<summary>Show answer</summary>

**Correct answer: B.** `DISTINCT` compares the whole selected row, so `(101, Biology 101)` and `(103, Biology 101)` are different pairs even though the titles match. Adding a column can stop duplicates from collapsing.

</details>

#### MCQ 17. A bug report says rows "usually come back in insertion order". What does SQL guarantee about order without `ORDER BY`?

A. Nothing; the server may return rows in any order
B. Insertion order is guaranteed
C. Primary-key order is guaranteed
D. Alphabetical order by the first column is guaranteed

<details>
<summary>Show answer</summary>

**Correct answer: A.** No `ORDER BY` means no guaranteed order. The server may return rows in any order, including a different order after statistics or indexes change.

</details>

#### MCQ 18. The same unordered query returns rows in a different order after a new index is added. What explains it?

A. The table gained duplicate rows
B. `DISTINCT` reordered the output
C. The data was updated during the run
D. Row order without `ORDER BY` was never guaranteed

<details>
<summary>Show answer</summary>

**Correct answer: D.** The order was never guaranteed; the index changed how the server chose to return the rows. Repeatable output requires an `ORDER BY` with a unique tiebreaker.

</details>

#### MCQ 19. A tester needs cards sorted by deck ascending and, within each deck, newest card first. Which clause does that?

A. `ORDER BY created_at DESC, deck_id ASC`
B. `ORDER BY deck_id DESC, created_at ASC`
C. `ORDER BY deck_id ASC, created_at DESC`
D. `ORDER BY deck_id, created_at`

<details>
<summary>Show answer</summary>

**Correct answer: C.** The first key sorts decks ascending, and the second key sorts newest first inside each deck. `ASC` is the default, and `DESC` reverses only its own key.

</details>

#### MCQ 20. `SELECT TOP (3) card_id, front FROM cards ORDER BY created_at DESC` returns which card IDs?

A. 1001, 1002, 1003
B. 1005, 1004, 1003
C. 1003, 1004, 1005
D. 1002, 1003, 1004

<details>
<summary>Show answer</summary>

**Correct answer: B.** Newest first: card 1005 (January 19), then 1004 (January 18), then 1003 (January 17).

</details>

#### MCQ 21. What does `TOP (3)` return when the query has no `ORDER BY`?

A. The three lowest primary keys
B. A syntax error
C. All rows that tie for third place
D. An arbitrary set of three rows

<details>
<summary>Show answer</summary>

**Correct answer: D.** `TOP` without `ORDER BY` is not a stable selection; the server may return any three rows, and a later run or plan can return a different set.

</details>

#### MCQ 22. A tester pages with `ORDER BY created_at ASC OFFSET 2 ROWS FETCH NEXT 2 ROWS ONLY`. Which cards come back?

A. 1001 and 1002
B. 1002 and 1003
C. 1003 and 1004
D. 1004 and 1005

<details>
<summary>Show answer</summary>

**Correct answer: C.** Ordered by `created_at` ascending, the cards run 1001, 1002, 1003, 1004, 1005. `OFFSET 2` skips 1001 and 1002, and `FETCH NEXT 2` returns 1003 and 1004.

</details>

#### MCQ 23. Which clause returns the first two rows in standard SQL?

A. `FETCH FIRST 2 ROWS ONLY`
B. `TOP (2)`
C. `OFFSET 2 ROWS ONLY`
D. `ORDER BY 2`

<details>
<summary>Show answer</summary>

**Correct answer: A.** Standard SQL has no `TOP`; the limit is `FETCH FIRST n ROWS ONLY`, placed after `ORDER BY`. `TOP` is SQL Server syntax, and `OFFSET 2 ROWS ONLY` skips rows rather than selecting them.

</details>

#### MCQ 24. A tester builds `display_name + ' <' + email + '>' AS label` and runs it for user 3. What does the label contain?

A. `(no name) <carol@example.com>`
B. ` <carol@example.com>` with an empty name part
C. `carol@example.com`
D. `NULL`

<details>
<summary>Show answer</summary>

**Correct answer: D.** SQL Server's `+` operator returns `NULL` when either operand is `NULL`, so user 3 gets a `NULL` label. `CONCAT` would return option B because it treats the missing name as an empty string.

</details>

## Part 3 — Filtering and NULL (17 questions)

#### MCQ 25. `WHERE` keeps a row when its condition evaluates to which value?

A. TRUE or UNKNOWN
B. TRUE only
C. FALSE
D. Anything other than `NULL`

<details>
<summary>Show answer</summary>

**Correct answer: B.** `WHERE` keeps only TRUE. Both FALSE and UNKNOWN remove the row, which is why a comparison with `NULL` silently drops it.

</details>

#### MCQ 26. Which predicate finds rows whose `display_name` is missing?

A. `display_name = NULL`
B. `display_name <> NULL`
C. `display_name IS NULL`
D. `display_name = ''`

<details>
<summary>Show answer</summary>

**Correct answer: C.** `IS NULL` is the predicate for a missing value and always returns TRUE or FALSE. `= NULL` and `<> NULL` are UNKNOWN for every row, and `= ''` looks for an empty string, not a missing value.

</details>

#### MCQ 27. `WHERE display_name = NULL` returns no rows, although user 3 has no name. Why?

A. `= NULL` is UNKNOWN for every row, and `WHERE` keeps only TRUE
B. The column is declared `NOT NULL`
C. The empty string sorts before every name
D. User 3 was removed by the foreign key

<details>
<summary>Show answer</summary>

**Correct answer: A.** `NULL = NULL` is UNKNOWN, so `= NULL` is UNKNOWN for every row and `WHERE` keeps nothing. User 3 is found with `IS NULL`.

</details>

#### MCQ 28. How does `WHERE a OR b AND c` group its conditions?

A. `(a OR b) AND c`
B. `a OR (b AND c)`
C. `(a AND b) OR c`
D. All three conditions are compared left to right

<details>
<summary>Show answer</summary>

**Correct answer: B.** `NOT` binds tighter than `AND`, and `AND` binds tighter than `OR`, so the condition parses as `a OR (b AND c)`. Parentheses are how a filter states a different grouping.

</details>

#### MCQ 29. A tester runs `WHERE card_id = 1001 OR card_id = 1002 AND rating = 5`. Which reviews come back?

A. 10001 only
B. 10001, 10002, and 10006
C. 10001 and 10002
D. No rows

<details>
<summary>Show answer</summary>

**Correct answer: C.** `AND` is evaluated first, so the filter means card 1001 at any rating, or card 1002 with rating 5. Reviews 10001 and 10002 are on card 1001 and survive; card 1002's reviews have ratings `NULL` and 2.

</details>

#### MCQ 30. `WHERE (card_id = 1001 OR card_id = 1002) AND rating = 5` returns which review?

A. 10001 and 10002
B. 10005
C. 10001 and 10006
D. 10001

<details>
<summary>Show answer</summary>

**Correct answer: D.** The parentheses apply `rating = 5` to both cards. Only review 10001 is a rating 5 on card 1001 or 1002; 10002 is a 4, 10003 is `NULL`, and 10006 is a 2.

</details>

#### MCQ 31. A tester expects `WHERE rating <> 5` to return every review that is not a 5. Which rows are silently excluded besides the rating-5 reviews?

A. 10001 and 10005
B. 10002 and 10004
C. 10003 and 10007
D. None; every non-5 row returns

<details>
<summary>Show answer</summary>

**Correct answer: C.** Reviews 10003 and 10007 have `NULL` ratings. `rating <> 5` is UNKNOWN for them, and `WHERE` drops UNKNOWN, so add `OR rating IS NULL` when the requirement means every non-5 review.

</details>

#### MCQ 32. `WHERE card_id IN (1001, 1004)` returns which reviews?

A. 10001, 10002, 10005, 10007
B. 10001, 10002, 10005
C. 10001 and 10005
D. 10001, 10002, 10005, 10006, 10007

<details>
<summary>Show answer</summary>

**Correct answer: A.** `IN` is shorthand for a chain of `OR` equalities. It does not look at `rating`, so review 10007 on card 1004 is included even though its rating is `NULL`.

</details>

#### MCQ 33. A tester asks for every review whose rating is from 2 through 4 inclusive. Which reviews match?

A. 10002 and 10004
B. 10002, 10004, 10006
C. 10003 and 10007
D. 10002, 10004, 10006, 10003, 10007

<details>
<summary>Show answer</summary>

**Correct answer: B.** `BETWEEN` includes both endpoints: ratings 4, 3, and 2 match. The two `NULL` ratings are excluded because the comparison is UNKNOWN for them.

</details>

#### MCQ 34. A tester means to include everything through January 25 with `reviewed_at BETWEEN '2026-01-20' AND '2026-01-25'`. Which review inside that intent is silently dropped?

A. 10005
B. 10007
C. None; both endpoints cover the whole day
D. 10006

<details>
<summary>Show answer</summary>

**Correct answer: D.** The bare upper bound means midnight at the start of January 25, so review 10006 at 14:00 is outside. Write `reviewed_at >=` the start and `<` the next day to include the whole last day.

</details>

#### MCQ 35. `email LIKE '____@example.com'` matches which users?

A. Dave and Erin
B. Alice and Carol
C. Alice, Carol, Dave, and Erin
D. All five users

<details>
<summary>Show answer</summary>

**Correct answer: A.** Each underscore matches exactly one character, so the pattern needs exactly four characters before `@`. Only `dave` and `erin` qualify; `alice` and `carol` have five and `bob` has three.

</details>

#### MCQ 36. A card front contains a literal percent sign. Which clause makes `LIKE` treat `%` as an ordinary character?

A. `COLLATE`
B. `TRIM`
C. `CAST`
D. `ESCAPE`

<details>
<summary>Show answer</summary>

**Correct answer: D.** `ESCAPE` declares the character that turns `%` or `_` into a literal, for example `LIKE '100!%%' ESCAPE '!'`. `COLLATE` changes case sensitivity, and `TRIM` and `CAST` do not affect wildcard meaning.

</details>

#### MCQ 37. A tester writes `card_id NOT IN (1001, NULL)` to exclude card 1001. How many rows come back?

A. 4
B. 0
C. 5
D. 1

<details>
<summary>Show answer</summary>

**Correct answer: B.** The predicate expands to `card_id <> 1001 AND card_id <> NULL`. The second comparison is UNKNOWN, and `TRUE AND UNKNOWN` is UNKNOWN, so no row passes.

</details>

#### MCQ 38. A tester's exclusion check `rating NOT IN (SELECT rating FROM reviews WHERE user_id = 1)` returns zero rows. Which change is a reliable fix?

A. Add `DISTINCT` inside the subquery
B. Change `NOT IN` to `=`
C. Add `rating IS NOT NULL` to the subquery
D. Add `ORDER BY rating` to the subquery

<details>
<summary>Show answer</summary>

**Correct answer: C.** The subquery returns 5, 3, and `NULL` for user 1. The `NULL` makes every `NOT IN` comparison UNKNOWN, so filtering it out with `rating IS NOT NULL`, or rewriting with `NOT EXISTS`, restores the intended rows.

</details>

#### MCQ 39. `COALESCE(display_name, '(no name)')` returns what for user 3?

A. `NULL`
B. An empty string
C. `Carol`
D. `(no name)`

<details>
<summary>Show answer</summary>

**Correct answer: D.** `COALESCE` returns its first non-`NULL` argument, so user 3 gets the display value `(no name)`. The stored value is still `NULL`; only the output changes.

</details>

#### MCQ 40. A developer guards a division with `NULLIF(COUNT(rating), 0)`. What does `NULLIF(a, b)` return when `a` equals `b`?

A. `NULL`
B. `a`
C. `b`
D. 0

<details>
<summary>Show answer</summary>

**Correct answer: A.** `NULLIF` returns `NULL` when both arguments are equal and returns the first argument otherwise. That is why `NULLIF(COUNT(rating), 0)` protects a division from a zero denominator.

</details>

#### MCQ 41. `TRUE AND UNKNOWN` evaluates to which value?

A. TRUE
B. UNKNOWN
C. FALSE
D. An error

<details>
<summary>Show answer</summary>

**Correct answer: B.** `TRUE AND UNKNOWN` is UNKNOWN: `AND` is TRUE only when both sides are TRUE. `WHERE` then drops the row, because UNKNOWN is not TRUE.

</details>

**Correct answer: D.** `COUNT(rating)` counts rows where `rating` is not `NULL`: five ratings exist. The two unrated reviews are not counted.

<details>

**Correct answer: B.** `COUNT(DISTINCT ...)` ignores `NULL` values and returns 3. `SELECT DISTINCT` keeps one row for the missing name, so the row count is 4.

#### MCQ 47. A report needs the total of all recorded ratings. What does `SUM(rating)` return?

B. 26
C. 21
D. `NULL`

<details>
<summary>Show answer</summary>

**Correct answer: A.** The five non-`NULL` ratings are 5, 4, 3, 5, and 2, which sum to 19. The two `NULL` ratings add nothing.

#### MCQ 48. Which denominator does `AVG(rating)` use on the sample rows?

B. 19, the rating sum
C. 2, the unrated reviews
D. 5, the reviews with a rating

<details>
<summary>Show answer</summary>

**Correct answer: D.** `AVG` ignores `NULL` inputs, so 19 is divided by 5 rather than 7. The fractional result 3.8 needs an explicit cast on SQL Server, because `AVG` over an `INT` returns an `INT`.

</details>

#### MCQ 49. A SQL Server query selects `AVG(rating)` and shows 3 instead of 3.8. Why?

<summary>Show answer</summary>

**Correct answer: C.** SQL Server's `AVG` over an `INT` column returns an `INT` and discards the fraction, so 19 / 5 appears as 3. Cast `rating` to `DECIMAL` before averaging to see 3.8.

</details>

#### MCQ 50. An aggregate query with `WHERE 1 = 0` still returns one row. Which values appear?

B. 0 for every aggregate
C. `NULL` for every aggregate
D. No row at all

<details>
<summary>Show answer</summary>

**Correct answer: A.** On an empty input, `COUNT` returns 0 while `SUM`, `AVG`, `MIN`, and `MAX` return `NULL` because they have no values to work on. Only `COUNT` is safe to add directly.

</details>

#### MCQ 51. A tester groups `cards` by `deck_id` and counts rows. Which result comes back?

A. 101: 2, 102: 1, 103: 2, 104: 0
B. 101: 2, 102: 1, 103: 2
C. 101: 2, 102: 1, 103: 2, 104: 1
D. One row with a count of 5

<details>
<summary>Show answer</summary>

**Correct answer: B.** `GROUP BY` returns one row per existing group: deck 101 has 2 cards, 102 has 1, and 103 has 2. Deck 104 has no cards, so it produces no group.

</details>

#### MCQ 52. Why does `GROUP BY deck_id` on `cards` leave out deck 104?

C. Its `is_public` value is 0
D. It has no cards, and `GROUP BY` groups only rows that exist

<details>
<summary>Show answer</summary>

**Correct answer: D.** `GROUP BY` groups the rows that exist; it does not invent a group for a parent with no children. A report that must list deck 104 starts from `decks` with a `LEFT JOIN`.

</details>

#### MCQ 53. A tester flags decks with more than one card. Which deck IDs does `GROUP BY deck_id HAVING COUNT(*) > 1` return?

A. 101 and 102
B. 101 and 103
C. 102 and 103
D. 104 only

<details>
<summary>Show answer</summary>

**Correct answer: B.** `HAVING` keeps groups whose count exceeds one, which is decks 101 and 103 with two cards each. Deck 102 has one card and is removed.

</details>

#### MCQ 54. Which clause filters groups after aggregation?

A. `WHERE`
B. `GROUP BY`
C. `HAVING`
D. `ORDER BY`

<details>
<summary>Show answer</summary>

B. Replace `ix_cards_deck_id` with `ix_cards_deck_front ON cards (deck_id) INCLUDE (front)` and drop the narrow index with approval; an Index Seek with no Key Lookup then covers this query, and `card_id` comes with the clustered key
C. Add `front` as the first key column and move `deck_id` to `INCLUDE`
D. Declare the index `UNIQUE`

<details>
<summary>Show answer</summary>

**Correct answer: B.** The seek finds the deck's rows, but `front` is not in the narrow index, so each row costs a Key Lookup. Replace the narrow index with one that adds `front` to the leaf with `INCLUDE`; `card_id` is already there as the clustered key. Do not keep both, because they share the key and differ only by the included column, and dropping the narrow index on a shared system needs approval. Covering is relative to one query, and the wider index also adds write cost and storage.

</details>

#### MCQ 138. A tester adds `WITH (NOLOCK)` to a baseline count so the check finishes faster. What is the risk?

A. It takes an exclusive lock on the table
B. It guarantees a transactionally consistent snapshot
C. It has no effect on correctness, only on speed
D. It can read uncommitted rows that later roll back and can repeat or miss rows during a scan, so the count may never have been true at one moment; it is a correctness risk, not a tuning fix

<details>
<summary>Show answer</summary>

**Correct answer: D.** `WITH (NOLOCK)` is the SQL Server table hint equivalent to `READUNCOMMITTED` for that reference. It skips shared locks but can read uncommitted rows that later roll back, read the same row twice or miss a row when pages move during a scan, and return a count that was never true at any single moment. It also does not guarantee zero blocking, because a schema change can still block the reader. Run release checks under the default isolation level, or name the level used.

</details>

#### MCQ 139. A parameterized review query is fast for a typical card and slow for a card with thousands of reviews; the same cached plan shows a large gap between estimated and actual rows. What is the evidence-based next step?

A. Treat parameter sniffing as the hypothesis: run the statement with a typical and an extreme value, compare estimated versus actual rows and logical reads, and if the cached plan is the cause, propose `OPTION (RECOMPILE)` for that statement and record the compile cost
B. Add `WITH (NOLOCK)` to the query
C. Add a clustered index on `reviews.rating`
D. Rewrite every query in the application

<details>
<summary>Show answer</summary>

**Correct answer: A.** Parameter sniffing means the cached plan was compiled from one set of parameter values whose estimates do not fit another. The evidence is the same plan shape with a large estimated-versus-actual gap across at least two parameter values, plus the logical reads and CPU time for each. If the cached plan is the cause, `OPTION (RECOMPILE)` fits a plan to each execution at the cost of a compile every time; it is a targeted T-SQL fix, not a default, and an index or refreshed statistics may be the better fix.

</details>

## Part 11 — Release QA Query Patterns (11 questions)

#### MCQ 140. A release moves card 1005 from deck 103 to deck 101 and changes no row counts. What does the four-table baseline show, and what does it prove?

A. All four counts are unchanged; equal counts are necessary but do not prove the data is unchanged, because a move keeps the count
B. The `cards` count drops to 4
C. The `decks` count rises to 5
D. The baseline reports the move automatically

<details>
<summary>Show answer</summary>

**Correct answer: A.** The baseline returns `users` 5, `decks` 4, `cards` 5, and `reviews` 7 before and after, because an `UPDATE` of `deck_id` moves a row without adding or removing one. Equal counts are necessary, not sufficient; a comparison at the key level is what shows the changed row. A count without an expected value is a fact, not yet a finding.

</details>

#### MCQ 141. A tester records one total of 21 rows across `users`, `decks`, `cards`, and `reviews` before and after a deployment. Why is that single total a poor baseline?

A. 21 is the correct total and is sufficient evidence
B. Counts belong to separate entities; one cross-table total can hide a gain in one table and a loss in another, so compare table by table in the same environment
C. `COUNT(*)` is not allowed before a release
D. A baseline must be captured only after the deployment

<details>
<summary>Show answer</summary>

**Correct answer: B.** The four counts are separate baselines; their sum is not a meaningful total across different entities. A release that adds a card and removes a review leaves 21 while changing two tables, so each table is compared on its own, in every environment being compared, with the build identifier and time recorded.

</details>

#### MCQ 142. A duplicate check runs `SELECT email, COUNT(*) FROM legacy_users GROUP BY email HAVING COUNT(*) > 1`. What does it return?

A. No rows; the staging table has a unique constraint on `email`
B. Four rows, one per user
C. One row: `alice@example.com` with count 2
D. Two rows, one for user 1 and one for user 3

<details>
<summary>Show answer</summary>

**Correct answer: C.** `GROUP BY email` returns one row per repeated value, not one row per user, so the result is the repeated address with its count. Users 1 and 3 are the candidates behind it, and a second query such as `SELECT user_id, email FROM legacy_users WHERE email = 'alice@example.com'` lists them. The staging table deliberately has no unique constraint, which is why the import can hold the duplicate.

</details>

#### MCQ 143. A tester groups `decks` by `title` alone and reports Biology 101 as a duplicate. What is wrong with the check?

A. Nothing; deck titles must be unique across the whole product
B. It should group by `deck_id` instead
C. It should use `DISTINCT` rather than `GROUP BY`
D. The rule is one title per user's list; Biology 101 belongs to users 1 and 2, so grouping by `title` alone asks a different question, and `GROUP BY title, user_id` returns no rows

<details>
<summary>Show answer</summary>

**Correct answer: D.** Decks 101 and 103 share the title but belong to different users, which the product rule allows. A duplicate check groups by the columns of the uniqueness rule; `GROUP BY title` alone flags an allowed repeat, while `GROUP BY title, user_id` returns no rows on this sample. Before calling a row a duplicate, write down the rule and state it in the report.

</details>

#### MCQ 144. `legacy_reviews` has no foreign keys. Which rows does the orphan check that `LEFT JOIN`s both `cards` and `users` and keeps rows where either parent key is `NULL` return?

A. All four staging rows
B. Review 20002 (missing card 9999) and review 20003 (missing user 9999)
C. Review 20002 only
D. Review 20003 only

<details>
<summary>Show answer</summary>

**Correct answer: B.** Review 20002 finds no card 9999, so `c.card_id` is `NULL`; review 20003 finds no user 9999, so `u.user_id` is `NULL`. Reviews 20001 and 20004 match both parents and are removed by the `WHERE` clause. Checking both parents in one query is what catches a review whose card is valid but whose user is missing.

</details>

#### MCQ 145. A release check queries `v_deck_card_counts` and separately runs `SELECT COUNT(*) FROM cards`. The view returns 4 decks with `card_count` values 2, 1, 2, and 0, and `SUM(card_count)` is 5; the base count is also 5. What does the comparison establish?

A. The view is wrong because deck 104 has no cards
B. `SUM(card_count)` should be 4, one per deck
C. The view and the base table agree on the card total, and deck 104 survives with 0; a deck that loses its last card appears as an empty deck, so keep the view definition under review because a view stores no rows
D. The comparison proves that no card changed deck

<details>
<summary>Show answer</summary>

**Correct answer: C.** The view starts from `decks` and counts `c.card_id`, so every card belongs to exactly one deck and `SUM(card_count)` should equal `COUNT(*)` on `cards`; the empty deck survives as a row with 0 instead of disappearing or counting as 1. If the two totals disagree, either the view or the base table changed, and the difference is the finding. A view stores no rows, so a change to its `LEFT JOIN` or its `COUNT` changes every check built on it.

</details>

#### MCQ 146. A null check returns user 3 for `WHERE display_name IS NULL`. What does that row prove?

A. Only that the user has no display name; the schema allows it, so report it as a bug only if the product rule requires a name
B. That the data is corrupt
C. That every `NOT NULL` constraint is missing
D. That the query is wrong, because `NULL` cannot be selected

<details>
<summary>Show answer</summary>

**Correct answer: A.** A null check is meaningful only against a named rule. `users.display_name` is nullable, so the row is legal in the schema; if the product requires a display name, it is a finding, and if an unnamed user is allowed, it is a description. The rating check has the same split: reviews 10003 and 10007 hold `NULL` ratings, and `ck_reviews_rating` bounds a rating only when one exists. Use `IS NULL` in the detecting predicate; `COALESCE` belongs in a display layer after the finding is reported, and `= NULL` never matches.

</details>

#### MCQ 147. A full outer join compares review counts per card before the 2026-02-01 boundary with the counts over every review now. Which row appears, and why are both `IS NULL` tests needed?

A. No rows; every count matches
B. Card 1001 with 2 before and 2 after, because a review was re-rated
C. Every card once, because a `FULL OUTER JOIN` lists all rows
D. Card 1004 with 1 before and 2 after; the `IS NULL` tests keep cards whose rows appear or disappear, because a comparison with a `NULL` count is UNKNOWN

<details>
<summary>Show answer</summary>

**Correct answer: D.** Card 1004 held review 10005 before the boundary and gained review 10007 after it, so its count rises from 1 to 2; the other cards have equal counts. If a card had reviews only on one side, the missing side's count is `NULL`, and `before_count <> after_count` is UNKNOWN rather than TRUE, so the third condition alone would drop the row. The `b.card_id IS NULL` and `a.card_id IS NULL` tests keep the appeared and disappeared rows.

</details>

#### MCQ 148. A release changes deck 104 from private to public without adding or removing a deck. Which check shows it?

A. The four-table baseline, because the deck count changes
B. No check can detect a visibility change
C. The `is_public` distribution moves from 2 private and 2 public to 1 private and 3 public while the total stays 4
D. The `reviews` rating distribution changes

<details>
<summary>Show answer</summary>

**Correct answer: C.** A distribution answers "did the mix change?" rather than "did the total change?" Decks 102 and 104 are private and 101 and 103 are public in the sample; flipping deck 104 moves one deck between the groups and leaves the total at 4. On SQL Server `is_public` is `BIT`, so the groups are 0 and 1; under the standard schema the same groups display as `FALSE` and `TRUE`. Investigate a shift by listing the rows in the changed group.

</details>

#### MCQ 149. A tester inserts fixtures with reserved key 900 in one transaction, runs the check, and rolls back. What proves cleanup, and what changes for a cross-session browser test?

A. A post-rollback count of the reserved keys returns 0; a cross-session test must commit, then delete reviews, cards, decks, and users by key in that order and verify zeros
B. The rollback is enough in every case, including a browser test on another connection
C. The `INSERT` messages are the proof that the rows are gone
D. A committed fixture may be left for the next tester

<details>
<summary>Show answer</summary>

**Correct answer: A.** The rollback removes every inserted row, but the evidence is the verification query returning 0 for the reserved keys after the rollback. A fixture in an uncommitted transaction is visible only to its session, so a browser test on another connection cannot see it; that test must commit the fixtures, run the check, then delete child-to-parent (`reviews`, `cards`, `decks`, `users`) and verify zeros. A committed fixture is real data and inflates every later baseline.

</details>

#### MCQ 150. A tester attaches a zero-row orphan result to a bug report as proof that no orphan exists. Which checklist question decides whether that zero is evidence?

A. Is the join type correct?
B. Is the result measured?
C. Is the ordering deterministic?
D. Is `NULL` handled?

<details>
<summary>Show answer</summary>

**Correct answer: B.** The measurement item asks whether the query states its expected row count, whether the actual count is recorded, and whether the query would have returned a row if the defect existed. A zero-row result is evidence only under that condition, together with the query text, environment, time, and count. For a performance claim, the same item adds the actual plan and logical reads; a check that was not measured is an opinion.

</details>
